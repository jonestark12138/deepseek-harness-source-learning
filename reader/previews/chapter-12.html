第12讲 · 缺少执行器，为什么配置写了还不能开工

源码基线：cd5ef8148158c3a752a658978873241fdf8e2bbc。业务案例为虚构 Java 运费服务；图与流程是教学推演，源码事实另有固定证据。

一、同一运费任务遇到的下一道障碍

第十一讲整理出排查流程，但实际运行时发现缺少文件能力。先别让模型重复请求：如果工作台压根没装上执行器，再好的提示也没有用。本讲把同一运费任务暂停在“能力未就绪”，检查配置从哪里来、覆盖了什么，以及插件是否真正激活。

教学故障设定是：报告监视插件的原配置有目录和超时，后层只修改超时，却把整份配置对象替换，导致目录字段消失。这个字段例子属于虚构插件，用来观察上游真实补丁算法，不冒充某个实际产品插件。

三格为同一运费任务的教学状态变化或故障对照。图不是实际运行日志；关键区别见各格说明。

二、四个角色：方案、套装、修改单、安装员

方案像车间选装单，决定选哪几套设备。Bundle（插件套装）是带配置与代码的分发单元。Patch（配置补丁）是对装配配置的修改指令。Loader（装配器）负责把 Entry（配置条目）接入插件系统。

看入口 bin.ts（命令行入口文件），它先解析命令，再在装配方案分支调用 runProfile()。传入的四项分别是环境快照、方案名、补丁文件列表、交给应用的参数。插件管理和配置打印是另外的分支，不必都启动整棵应用树。

随后，loadProfile()（方案读取函数） 读取方案的 package.json，看 dsh.profile.bundles 数组。下面是便于辨认结构的教学示例，使用本仓库已有的套装名称：

{
  "dsh": {
    "profile": {
      "bundles": [
        "@deepseek-ai/dsh-base",
        "@deepseek-ai/dsh-web-app"
      ]
    }
  }
}

数组表达套装层的应用顺序。每个套装自己的清单再用 dsh.bundle.patch 指出补丁文件。例如基础套装提供 cordis.patch.yml，在里面用 insert 插入模型、会话、工具等配置行。

这里出现第五个词：配置行（配置条目），就是“要安装哪个插件、给它什么配置、是否禁用”等信息组成的一项记录。id 是该行的定位编号，name 通常是加载模块的名称。它们不等于插件运行实例。

为什么根配置竟然是空数组？

prepareProfile()（方案准备函数） 每次把方案目录里的 cordis.yml 写回 []。这不矛盾：场地先清空，设备由后面的套装和补丁插入。

文件存在还给加载流程一个目录锚点，便于解析相对路径。源码注释解释了重写原因：装配器的写回可能把已经组合的行留在根文件里；下次再应用套装 insert（插入配置行），就会重复插入。根配置是起点，最终配置是计算结果。 因此日常调整应进入相应补丁文件，而不是把这份空根文件当总配置去维护。

三、同一行被改了几次，谁最后说了算？

先看全貌，再看函数。把补丁想成轮流批改同一张装配清单：套装给初稿，方案做专项调整，本机偏好再改，本次命令还可以追加修改。

allPatches()（补丁排序函数） 是最短的顺序证据：

return [
  ...composed.bundlePatches,
  ...composed.profile.patches,
  ...composed.homePatches,
  ...composed.overlays,
]

只关注数组展开的先后。套装按方案列出的顺序展开；之后是方案自己的 cordis.patch.yml；再是运行支撑系统主目录中的同名补丁；最后是叠加层（追加覆盖层），包括按参数顺序读取的 --patch 文件。

“主目录”在这里指由 resolveDshHome() 解析的运行支撑系统数据目录，不是当前仓库目录。方案补丁只影响这个方案，本机补丁影响经过该启动入口的各个方案。

composeProfile()（方案组合函数） 还可能在追加覆盖层最后加一条遥测禁用补丁：相关环境变量非空，并且配置里确有遥测行时，追加 disabled: true。所以“命令行永远最高优先级”不够准确。也不要据此扩展成所有环境变量都能覆盖所有 YAML（配置数据格式）字段；这里只核对了这一项显式逻辑。

现在可以回答开头的第一种故障：方案文件看起来改对了，但用户数据层或本次 Overlay（追加覆盖层）又写了同一字段，最后生效的值就可能不同。

四、最容易踩坑的地方：改的是哪一层？

“后写覆盖前写”还少了一个关键细节：覆盖粒度。

applyEntryPatches()（配置行补丁算法） 先复制输入并按行定位编号建索引，然后依次处理补丁。insert 添加新行，普通补丁用 id 找到旧行。真正修改的核心只有几行：

for (const [key, value] of Object.entries(overrides)) {
  if (key === 'id') continue
  target[key] = value
}

这是配置条目顶层赋值。如果键是 disabled，改的是禁用标记；如果键是 config，换的就是整个配置对象。

下面用一个虚构插件做纸面实验。字段只为展示补丁算法，不属于项目某个真实插件：

# 第一层：插入设备配置
- insert:
    - id: demo
      name: demo-plugin
      config:
        directory: reports
        timeout: 30

第二层：

- id: demo
  config:
    timeout: 60

两层应用后，demo（教学示例行）的配置对象是 { timeout: 60 }，没有 directory（目录字段）。旧页整张换掉了。若希望保留目录，第二层就要明确写上它。之后某插件是否通过自己的配置解析补默认目录，是另一个阶段，不能说补丁算法保留了旧值。

再做三个小判断：

改法 此阶段结果 为什么
只写 disabled: true 原配置对象保留 没覆盖配置对象字段
指向不存在的定位编号 告警并跳过该补丁 查不到修改对象
定位编号命中，但给了不同的名称 告警并跳过 名称在这里是目标匹配护栏，不是重命名指令

插入行会立即加入索引，因此后面的补丁可以修改前面刚插入的行。这一点由配置组合测试交叉验证。不要把所有无效补丁都想成“启动立即失败”：未命中定位编号的情况在这个函数里是告警并跳过。

4.1 真正运行补丁函数，而不是自己重写一个“类似算法”

现在把纸面例子交给实际的配置行补丁函数。我们不复制函数实现到教材里冒充验证，而是在独立实验脚本中导入固定提交的上游代码，构造虚构报告插件配置。实验同时断言两个对象：输出只剩超时 60，输入仍保留目录和超时 30。第二个断言非常重要，否则一个“看起来结果正确”的实现可能偷偷污染后续热更新的基准。

再改变输入：第一条补丁插入报告行，第二条立刻将该行禁用，第三条指向不存在的编号。预期为“插入行被禁用、产生一条告警”，不是三个动作全失败。对应关键状态是索引在插入后已更新；这个结论能解释为什么同一层后面的补丁找得到刚插入的行。

实验代码与统一运行命令收录于第十五讲工程实验，其中前两项就是本讲。运行记录是实际导入上游函数的内存测试，不涉及安装真实插件或改用户配置。

一个常见设计取舍是浅层替换还是递归合并：前者让“这层提供完整配置对象”的语义明确，却容易漏写旧字段；后者写补丁方便，但删除字段、数组合并和默认值优先级又必须另定规则。本仓库此路径选择前者。理解它不是说它一定更好，而是能预测真实行为并为配置审查设计断言。

五、纸面装好了，运行为什么还可能失败？

前面处理的全是配置数据。现在才轮到安装员。

boot() 先建立根插件上下文，也就是服务查找与局部信息的入口，再装配加载机制。这里还不需要先读第十三讲：把上下文理解成工作台的通讯录即可。配置文件入口负责读配置文件并应用补丁，装配器把配置条目连接到 Cordis 的插件安装过程。一个配置行可能对应一个插件，也可能是承载子树的分组或文件入口。

把boot()（启动与验收函数） 的主体按职责读，可以看到：

  1. 建根插件上下文，设置路径等宿主信息。
  2. 安装装配器。
  3. 执行宿主准备回调 prepare，让环境与命令行服务先可用。
  4. 挂载根 Include（配置文件入口），进入配置树装配。
  5. 等待加载树收敛，再检查启用行是否真正激活。

“收敛”先理解成：这一轮正在推进的装配处理告一段落。它本身不等于所有启用插件都成功，所以后面还有激活审计。

插件的每次安装都有一个运行实例，源码称为 Fiber（插件安装实例）；它根据声明的必需服务决定能否加载。第十三、十四讲将继续拆开这项机制。设备已经送到门口，但电源没接好，不能算验收通过。

assertEntriesActivated()（激活审计） 把问题进一步分开：模块没能加载出来；插件初始化失败；或者插件仍在等待某个服务。disabled（禁用标记）行不参加“必须可用”的要求。初始化失败会保留相关错误信息，缺依赖则列出等待的服务名。

boot() 捕获启动异常后会释放根插件安装实例，回收已经装上的部分，再包装错误抛出。因此不能把启动器画成“碰到坏设备仍一路前进，最后总会返回成功”。

还有一个源码中的特殊情况：某个一次性应用在启动窗口内主动完成并释放整棵树，装配器已不存在时会提前返回。它不是“仍存活的树通过了激活审计”。正常运行与主动结束要按实际分支区分。

为什么不能按 YAML（配置数据格式）行顺序推断激活顺序？

基础套装注释已明确提醒：行顺序不携带加载语义，激活取决于服务可用性。更底层的依据在 Fiber._refresh()（安装实例的依赖刷新方法），它检查注入的服务实现，决定进入加载还是卸载。

配置应用像改清单，依赖激活像接好电才允许开机。这两条顺序解决不同问题。

六、改完文件，为什么有时要重新启动？

方案的 patchReload 决定本次运行怎样对待用户补丁变化。live 表示运行中监听并重新组合；startup 表示启动时应用，本次运行不安装这条监听路径。

这不表示仅启动时应用模式忽略用户配置。两种模式都先应用用户层，差别在启动以后是否跟随修改。runProfile()（方案启动函数） 后半段明确用条件分支安装监听与提交就绪通知。

这是本讲与“热更新”之间的边界。你只需要知道到哪里查，不必现在就读完事务回滚和文件监听。

工程追踪补充

Patch（配置补丁）不是递归合并承诺；Activation（激活）是条件满足后实际运行成功，不是条目写在文件中。

词典用于回查，正文在首次使用处解释。代码、参数与路径保留原拼写；产品名称不逐字翻译。模型上下文和插件上下文不是一回事。

Bundle（插件套装）

带配置和代码的分发套装，像按用途打包的一箱工作台零件。套装存在不表示其中每个插件都已激活。

Patch（配置补丁）

针对装配配置的修改指令，像修改施工清单。本讲是配置补丁，不是 Java 源码补丁；某字段替换整个对象时不能假定自动深合并。

Loader（装配器）

把配置条目接入插件系统的装配器，像按清单安装设备的工人。它与模型服务不同，装配成功也不代表业务测试通过。

Entry（配置条目）

配置树里的一项插件安装条目，像清单上的一行，带定位信息和配置。定位编号用来命中目标，不是插件已工作的凭据。

bin.ts（命令行入口文件）

命令行入口文件：解析命令后进入相应启动路径。像接单窗口，不是所有业务机制都在入口里实现。

YAML（配置数据格式）

表达配置数据的格式，像清单的书写规则。缩进和字段值能影响解析结果，但格式本身不负责安装插件。

Overlay（追加覆盖层）

在前面配置之上追加的覆盖层，像施工单后附的更改单。要按实际组合顺序判断最终值，不能只看最初一层。

demo（教学示例行）

正文配置推演中使用的虚构定位编号，用来演示某行配置被命中。不是要求读者安装的真实插件。

Include（配置文件入口）

读取并装配配置树的入口，像施工清单入口处的整理台。配置行改写、插件安装与依赖激活仍是不同步骤。

Fiber（插件安装实例）

插件的一次安装实例，像同一款设备的一次具体装机。它持有当前安装的资源与清理责任，不是线程或协程的同义词。

loadProfile（方案读取函数）

读取装配方案的函数，帮助追查套装和相关补丁来源。像找到原始施工单；函数名不代替对其返回值和错误路径的阅读。

allPatches（补丁排序函数）

确定补丁组合次序的源码入口，像把更改单按生效顺序排好。顺序影响覆盖结果，但不能由这个名字推断所有字段都深合并。

composeProfile（方案组合函数）

组合装配方案的函数，像把基础清单和覆盖层整理成待装配材料。组合配置与运行插件是不同责任。

applyEntryPatches（应用配置行补丁的函数）

对命中的配置条目应用修改的函数，像按编号改施工单的一行。具体字段可能整体替换，需核对正文示例及源码。

assertEntriesActivated（激活审计函数）

核查应激活条目是否实际激活的审计函数，像装机后查设备是否真的到位。未激活要分清缺服务、加载或初始化失败，不等于验收业务功能。
