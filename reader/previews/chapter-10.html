逐步讲解

第10讲 · 一个查契约，一个查实现，结果怎样合回来

源码基线：cd5ef8148158c3a752a658978873241fdf8e2bbc。业务案例为虚构 Java 运费服务；图与流程是教学推演，源码事实另有固定证据。

一、上下文放得下，也不意味着该由一个人全读

第九讲把长材料变成带出处的摘要。现在同一运费任务又增加两个模块：业务约定由一个模块维护，实际收费由另一个模块实现。两组证据可以独立查找，最后必须合并才能判断原因。

Subagent（子智能体）是主助手委派的另一个任务执行者，可以拥有自己的输入、运行状态和结果。它不是把原模型的一段推理免费拆成两份，也不保证能力更强。它会增加启动、材料交接、汇总与核对成本；问题很小时，一个助手直接完成反而更清晰。

三格为同一运费任务的教学状态变化或故障对照。图不是实际运行日志；关键区别见各格说明。

二、分的是证据任务，不是互相等候的半句话

可以给甲任务：“只读取业务约定，报告阈值是否包含等于，给出处，不要修改。”给乙任务：“只读取运费实现和失败测试，列出输入、分支与实际值，不要修改。”

主助手留在中间核对两份结论。甲不需要等乙，乙不需要等甲；二者都不能自己宣布全任务完成。如果让甲负责“先猜原因”，乙负责“等甲说完再确认”，并没有形成有用的并行。

同样，两个执行者同时修改同一行会制造冲突。读证据的任务容易并行，写同一文件的任务必须明确所有权和协调。子任务不是规避用户“不要修改”的办法。

三、源码先检查提供者能力，再创建工作

以下是固定提交中的定位片段（连续原文；中文说明放在代码之外）：

  async start(name: string, request: SubagentStartRequest): Promise<SubagentRun> {
    const provider = this.expectProvider(name)
    this.assertCapabilities(provider, request)
    assertSubagentMaxDepth(request.maxDepth)
    if (request.outputSchema !== undefined) assertObjectJsonSchema(request.outputSchema)
    const descriptor = snapshotSubagentDescriptor({
      mode: 'one-shot',
      provider: name,
      ...request.label !== undefined ? { label: request.label } : {},
    })
    const resolved: ResolvedSubagentStartRequest = { ...request, descriptor }
    return observeRun(this.emitLifecycle, name, request.parent, await provider.start(resolved))
  }

这段先找提供者，再检查能力、最大深度和结构化输出要求，然后生成子任务描述并调用提供者。不是任意后端都支持相同选项；调用者请求了不支持的能力，服务会拒绝，而不是静默丢弃要求。

Provider（子智能体提供者）可能创建进程内助手，也可能通过另一运行环境委派任务。能力是否隔离、工作区怎样传递、取消如何落实，必须看所选实现。不能由“子”这个字推断它有独立容器或独立磁盘。

3.1 这次选进程内新建，沿提供者继续追下去

本例选择 Spawn（从新会话开始创建）式的进程内提供者，不默认复制父会话。提供者实现明确声明不继承父对话，并把请求交给共享驱动。它有自己的会话和提示，但仍在同一进程、同一服务环境中运行，因此独立会话不等于独立文件系统或安全隔离。

这会直接影响怎么交代任务：父助手不能只说“照刚才的要求查一下”。甲收到的请求至少要有运费案例的范围、约定位置、要求输出阈值是否含等于以及不修改的限制。乙同样要有实现与报告的定位。新建子会话不会凭空知道父助手刚读过哪份文件；这和第三讲“磁盘存在不等于模型看见”是同一条原则。

继续看共享进程内驱动：它检查深度和取消，生成子会话身份，捕获委派时的策略覆盖，再通过代理工厂创建子实例。创建窗口内施加工具过滤、角色提示和可选结构化输出约束，发布成功后交给运行包装器驱动一轮工作。

工具过滤与角色提示不在同一个层级。过滤决定这个子实例实际可使用什么；提示告诉模型应如何判断和表达。把“只读”写进任务可以帮助理解，但不应该因此省略执行侧限制。父助手之后切换配置，也不能反过来改写子任务启动时已经捕获的策略快照。

3.2 为什么返回一个运行句柄，而不是只返回字符串

Run Handle（运行句柄）像领走一张工位使用票：它既告诉你是哪项工作，也带着等待结果、取消和清理的责任。提供者启动承诺完成，意味着子实例已经发布并把这些责任交给持有者；不代表子任务结果已经完成。启动承诺拒绝，则尚未交出句柄，不能要求调用者清理一个从没拿到的运行对象。

发布后的驱动把父取消信号接到子实例，补做一次信号检查来覆盖创建与运行监听交接的空隙，然后投递子任务提示并等待空闲。结果从这次激活边界之后的事件中读取，避免把历史输出当成本次交卷。清理时要等待实例处置与结果通道都收束；不能在子任务还持有资源时先报告“结束了”。

上游结果收束测试区分正常完成、被取消、错误、输出上限等原因，还验证报告前的清理以及清理失败不会伪装成普通成功。这与第十三讲的资源生命周期形成衔接：分工带来的不只是多一个回答，还多了一份资源责任。

四、一次性交卷与能继续对话的子助手

一次性子任务适合甲乙各交一份证据报告。Continuable Subagent（可继续的子智能体）则保留可持续追问的子会话；例如乙查完收费实现后，还要继续查调用方如何转换金额。

继续子任务入口 明确区分“消息被收件队列接受”和“轮次已经执行或完成”。得到子会话编号不是得到结果；后续消息也不是任意插入当前推理，而是按其队列契约进入后续轮次。

本书前面已学过日志和恢复，所以这里无需发明新的神奇记忆：可继续子任务仍依赖会话记录、活动实例与明确的父子权限关系。

五、后台工作、目标和定时提醒分别解决什么

Job（后台作业）适合已知的长时间动作，例如测试命令还在运行，主助手可以先整理证据。它有状态、输出和取消责任，不等于一个会推理的子智能体。后台作业职责 区分契约、进程内实现和面向模型的控制工具。

Goal（持续目标）记录跨轮次要完成什么，但不是调度器；只安装目标状态服务不会自动开始工作。目标说明 特别区分持久目标与进程内继续许可。

Schedule（定时提醒）解决未来何时投递跟进消息，不保证关闭会话后后台一直有活跃模型。固定源码的 提醒说明 说明冷会话的到期提醒要等后续活跃实例承接。

六、合并以后仍由主助手负责验真

两份报告要给同一案例的文件、版本、关键行与未验证部分。结论冲突时回到原材料，不按谁说得更自信投票。子任务说“测试全过”也不能替代当前代码上的测试结果。

具体交卷可以要求四个字段：观察到的事实、文件及版本、支持事实的位置、尚未验证之处。甲说“约定包含等于”，乙说“实现使用严格大于”，主助手才能结合失败输入推导边界缺陷；如果乙读到的是另一个分支的代码，两个流畅结论仍然不能拼出可靠诊断。

是否值得分工也要计算。本例文件很少，单助手顺读更简单；当约定、调用链与实现分散且彼此可独立检索时，才可能节省时间。理想并行耗时接近最慢子任务加交接与核对，而不是零成本除以人数。共享模型限额、重复读取和汇总失败还可能让它更慢。真正的优化对象是独立工作量，不是机器人数量。

本讲不为展示而真的启动付费多模型任务。作者实际执行的是上游可控测试：

node node_modules/vitest/vitest.mjs run packages/subagent/subagent/tests/run-settlement.spec.ts packages/subagent/subagent-spawn-in-process/tests/subagent-spawn-in-process.spec.ts --maxWorkers=1 --no-file-parallelism

它们已包含在第八至十讲四文件 274 项通过的验证批次中。练习请预测“启动前失败”“发布后失败”“结果正常但清理失败”三种所有权与最终结果，再读断言验证；不要把创建了子会话编号当成任务已经完成。

工程练习：不是多开两个窗口就叫分工

  1. 新建式子助手不继承父对话，父助手只发“按刚才说的查约定”，会缺什么？写一份包含材料定位、只读范围、输出证据与未验证项的完整任务。
  2. 启动前提供者拒绝、发布后执行失败、结果正常但清理失败，分别由谁负责，能报告同一种成功吗？
  3. 两个子助手结论相同，但源码版本不同，主助手能直接采纳吗？
  4. 约定和实现只有几十行，为什么不一定值得分工？列出新增耗时和资源责任。
参考答案

不能依赖未继承的“刚才”。发布前没有句柄交给调用者，提供者负责未发布资源；发布后句柄持有者负责结果与处置，清理失败也不能藏成普通成功。版本冲突要回原材料核对，不靠投票。启动、重复上下文、等待最慢子任务、结果合并、取消和清理都是成本。独立任务量大于这些成本时才值得采用。

词典用于回查，正文在首次使用处解释。代码、参数与路径保留原拼写；产品名称不逐字翻译。模型上下文和插件上下文不是一回事。

Subagent（子智能体）

受委派处理独立任务的另一个智能体，像一位查业务约定、另一位查实现的同事。分工结果仍要主助手核对，不自动扩大修改权限。

Provider（子智能体提供者）

负责创建与管理子任务的提供者，像任务派发渠道。可能进程内执行，也可能走别的运行环境，不能只凭子智能体这个名字推断隔离强度。

Continuable Subagent（可继续的子智能体）

可接收后续追问的子任务会话，像同一位同事查完收费逻辑后继续查金额转换。接收追问不等于已经完成新任务，也不保证同一个系统进程。

Job（后台作业）

可持续运行并查询状态的后台作业，像测试工位还在执行命令。作业运行中不是成功，需等实际完成与结果。

Goal（持续目标）

跨轮次保存待完成目标的记录，像工单顶部一直保留的验收目标。它不是调度器，目标存在不表示系统关机后还在工作。

Schedule（定时提醒）

在满足时间条件时触发提醒或输入的调度能力，像日历闹钟。它不替代目标、作业或真实进程，离线期间的处理需看具体恢复契约。
