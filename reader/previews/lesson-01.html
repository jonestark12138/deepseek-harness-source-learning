第一讲逐步讲解 · 跟着一次测试排查，走进工作室

源码快照：cd5ef8148158c3a752a658978873241fdf8e2bbc。比喻帮助理解，结论以该快照的源码与维护文档为准。

一、先别管术语：它真的看过报告吗？

假设我们正在维护一个 Java 服务，刚改完校验逻辑，一条测试失败了。你对助手说：“帮我找原因。”下面是为讲解而设计的场景，不代表教材生成时实际运行了这条测试。

助手回答：“可能是边界条件没覆盖。”这句话听起来合理，但你会追问：哪条断言？预期值是什么？实际值是什么？它是否真的打开过报告？

这个追问很重要。一句像样的解释，只能证明生成了这句话，不能证明读取或执行已经发生。

Model（模型）接收提供给它的上下文，推理并生成输出。输出可能是文字，也可能包含Tool（工具）调用请求。模型像大脑：能判断“应该去看报告”，但这个判断还不是一次文件读取。

让请求真的接到工具、把结果带回来、留下过程记录，再决定是否继续，需要模型之外的Harness（运行支撑系统）。

本图：这里说的是整体助手的教学近似。源码中的智能体是具体运行对象的控制句柄，不能拿图中的等式直接定义它。

回到真实项目。 模型调用包 负责不依赖具体厂商的调用接口和共享消息词汇；具体适配器处理厂商差异。智能体包 提供运行对象的句柄、登记与事件，默认创建和驱动由 Agent Loop（智能体循环驱动）提供。这套循环像安排“下一步做什么”的值班流程，但不是大脑本身，也不是整个运行支撑系统。

现在只记一个区别：会推理是模型的能力，把推理嵌进可持续工作过程是系统的工作。

二、先看完整任务：证据怎样推动下一步

先暂时把工作台如何装好放到一边，假设所需能力已经可用。用户的排查请求到了，下面只展示“可能需要调用工具”的一种教学路径。

本图只画了需要工具的一种路径。模型不一定调用工具；工具也可能被拒绝或失败。故事次序不代表所有底层事件的精确发生顺序。

先是输入被接收并进入处理流程。随后模型拿到本次提供的信息，可能提出工具请求。运行支撑组织一次受保护的执行尝试，结果或拒绝信息影响后续判断；相关过程进入Session（会话）记录。还有事情需要模型继续处理时，再发起后续模型请求。

架构文档的一轮处理流程 明确区分：Step（一步模型交互）是一次模型请求加上其工具调用；Turn（一轮处理）可以包含零个或多个步骤。输入接收不是一步模型交互的定义，模型直接回答也是正常分支。

所以不要把助手想成“模型一次性吐出全部正确动作”的流水线。更有用的画面是：看证据，做一次受约束的尝试，再看结果。 本讲不保证它一定查对，也不保证每个请求都会被允许。

接着把这条路径放进同一份教学案例：读到报告后，发现“预期拒绝负数，实际却通过”；助手再请求查看校验代码，比较断言与分支，然后说明原因。此时用户只授权排查，流程不能自行改代码。只有用户进一步同意修复，才进入修改与相关测试；测试失败就重新收集证据，测试通过也只说明已执行的检查通过，不能概括成所有问题消失。

整个过程像工程师查故障时反复翻报告、看代码、做验证。不同之处是：模型负责提出判断和下一步请求，程序负责组织调用、接回结果和维持状态。一次模型输出既不是整次任务，也不是执行证明。

三、拿到手册，不等于拿到了扳手

我们已经看见完整路径，现在把每一步用到的东西从工作台上分开。我们希望助手先看失败断言，再核对相关代码，最后用证据解释原因。这里开始需要五件不同的东西。

本图：同一台面表示这些职责共同支撑任务，不表示它们在源码中依次调用。

1. 扳手：动作真的发生在这里

工具是对模型暴露的可调用动作及其受保护的执行路径。模型可能请求“读某个文件”，工具系统负责查找相应实现，并经过策略等环节尝试执行。

联想到 Java 后端：方法签名说明“能请求什么”，实现才真正做事，拦截器或权限检查还可能拒绝请求。但这只是帮助入门，并不是说工具注册就是 Spring MVC（Java 网络请求处理框架）。

工具包的职责说明 同时提到工具定义与执行管线，所以我们不能把“模型看到了工具说明”写成“它已经有权限执行”。

2. 手册：告诉它怎样做，不替它做

Skill（技能指令）是一组可复用的任务指令。可以像团队的故障排查手册：先收集什么证据、按什么顺序判断、如何输出结果。

手册里写“运行相关测试”，不会自己启动进程。真正执行仍要靠工具；是否允许执行仍受执行策略约束。反过来，有测试工具但没有合适方法，助手也可能查错方向。

技能包 还区分提供指令的来源、汇总目录和加载使用的一侧。第一讲知道“可发现、可加载的指令”即可，暂不拆内部机制。

3. 日志：记的是经过，不是凭空多一个大脑

会话像工作日志。用户输入、模型输出以及工作过程中相关事件形成可追加的记录。需要下一次模型请求时，可以从日志派生消息。

这里有两个容易漏掉的限制。第一，日志不等于每次原样、全量送给模型的内容。第二，日志能力不等于已经可靠地落盘；持久化是独立后端的职责。会话包 对追加事件、deriveMessages（消息派生方法） 和独立持久化有明确说明。

你可以联想到事件日志与读模型：同一份历史可以组织成供特定用途读取的结果。不过本讲不把它与某个 Java 事件溯源框架画等号。

4. 资料夹与护栏：材料在哪儿，动作能到哪儿

文件系统能力让系统读写文件材料；文件工具再把相关能力呈现为模型可请求的动作。它不是模型训练时记住的知识。文件能力组 区分接口、实现和面向模型的工具。

沙箱在本项目的这组包中，主要对子进程执行的文件影响范围施加策略。护栏这个比喻只是说“有约束”，并不等于绝对安全。也不能把它直接换成 Docker（容器工具）：同一环境中的限制，与容器、虚拟机或远程执行环境的替换不是一回事。沙箱边界说明。

把这个故事翻译成一句话：手册提示怎么查，工具尝试动作，资料夹提供材料，日志保留经过，护栏约束范围。大脑根据得到的证据继续判断。

四、为什么连“核心”都做成插件？

想象一个主函数同时写死模型调用、工具列表、日志保存和循环逻辑。你只想更换日志后端，却要小心别碰坏整个工作流程。

这并不是说本项目曾经这样实现过，而是一个用于理解设计价值的反例。可插拔的价值，在于让能力有相对稳定的边界，并由框架管理装配和生命周期，而不是每次都重写整台机器。

本图：工作台比喻插件组织框架，不是硬件、操作系统或沙箱；模块化也不意味着任意实现都兼容。

Plugin（插件定义）可以贡献可调用的服务、类型化事件或可回收的副作用。Service（服务能力）在这里先理解成“通过稳定名称提供给其他插件的能力”；Event（事件）则让多个参与者围绕某件事协作。

Context（插件上下文）是查找这些服务的入口，例如 ctx.tools（工具服务）、ctx.llm（模型调用入口）、ctx.sessions（会话服务）。注意，同样叫“上下文”，它不是每次交给模型的那份提示和消息。

Cordis 是组织这些插件的框架。Cordis 入门 给出三个现在就有用的规则：

  • 用稳定的服务键找到能力，不要求消费者直接导入某个具体实现。
  • 通过声明必需服务，依赖满足后才能激活，而不是仅看文件位置。
  • 注册监听器、提示片段等副作用时保留回收机制，卸载或重载时能够清理。

这和 Spring 的依赖注入、生命周期管理有相似的入门直觉；但别把 ApplicationContext（Spring 应用容器）、受容器管理的对象、Cordis 插件上下文和插件定义逐个机械对号入座。我们接下来读的是真实服务键、插件配置和注入声明。

“核心也是插件”的直接证据在 架构说明：模型适配器、工具注册、会话日志、循环本身都按插件组织。再去基础套装里找对应配置行，才能把这个说法落地。

五、现在只找三处证据，不必先读完整启动器

第一处看默认循环的请求边界：循环先从会话取得派生消息，再组装模型请求。这里证明“模型看到什么”需要程序准备，不是日志自己跑去找模型。

第二处看会话追加记录：发生的事情进入日志。第五讲会沿这处入口解释为何要快照、验证与冻结。

第三处看基础套装的配置：模型、会话、工具和循环以插件配置出现。它证明装配意图，不证明插件已经运行成功。

如果此时被类型语法挡住，去第二、三讲补对应语法；如果被目录层次挡住，去第四讲补工程地图。不要为了“按编号学完”而忘掉最初的测试问题。

六、装配留给第九讲，先知道它解决什么

装配方案决定选择哪些插件套装；配置补丁调整清单；装配器把清单接到插件安装。像按选装单把工作台搭好，而不是给模型换一种推理算法。

这里先记住两个边界：配置补丁应用顺序不等于插件激活顺序；替换整份配置也不等于逐项深合并。第九讲会用同一张清单把这两个问题展开。现在无需背启动器所有函数名。

七、下一讲不是又开一个新故事

你应该能解释：助手为什么要先看报告，为什么工具请求不等于执行成功，为什么要记录结果，以及授权修复后为何仍要测试。这样就已抓到可迁移的Agent（智能体）工作直觉：围绕任务组织信息、提出动作、受约束地执行、观察结果并决定继续或停止。

不同系统在模型接口、记忆、权限、调度和执行环境上会有区别，不能从这个共同直觉推出实现完全相同。我们用 DeepSeek Harness 学的是可核对的机制，不是宣布所有产品内部都一样。

主线下一站是第五讲：沿会话日志读懂一个包。问题顺势变成：第一次读到的报告，怎样进入第二次请求？练习与词典都围绕这条任务链使用。

练习与答案

第1讲练习与答案

先独立解释，再展开答案。每题都要求把结论接回任务，不以记住英文拼写作为通过标准。

1. 只让排查，能直接改代码吗？

助手已找到可疑校验逻辑，是否可以马上修复？

展开答案与理由

不能仅凭“帮我找原因”推断用户授权修改。先解释证据和原因；用户同意修复后，才进入修改与验证。推理到一个动作，与获得执行授权是两回事。

2. 手册等于工具吗？

已经加载排查手册，但没有执行命令的工具，能运行测试吗？

展开答案与理由

不能。手册提示方法，工具实现动作；执行还需要相应环境与允许条件。

3. 报告为什么还要记录？

第一次模型请求读到了报告，第二次是否天然还能看到？

展开答案与理由

不能假定。程序需要保存相关经过，并组织下一次请求提供的消息。会话日志支撑这一点，但不等于每次把全部日志原样发送。

4. 模型直接回答是否出错？

一次简单问题没有任何工具请求，是否说明循环失败？

展开答案与理由

不一定。模型可以直接作答。工具是按任务需要选择的路径；是否正确要看证据需求，而不是工具调用次数。

5. 把一句话拆成证据链

“助手说修好了，所以问题已解决”，缺了哪些证据？

展开答案与理由

至少区分修改是否获准、是否真正写入、哪些验证实际执行、结果是什么。部分测试通过不等于所有场景正确。请回正文定位模型、工具、日志分别承担什么职责。

术语词典

第1讲术语与比喻词典

遇到陌生词，先回到这个问题：助手为什么不能只靠一次回答完成测试排查？ 以下是查阅页，正文会在需要时解释关键概念。英文只用于和源码对照；它不是额外的背诵任务。

英文与中文 直觉、实际职责与边界
Model（模型） 拿到材料后推理并生成输出，像分析问题的大脑；不会凭一句话证明动作已执行。
Harness（运行支撑系统） 像带工具、日志和规则的工作室，把推理接入实际工作过程；不只是工具列表。
Agent（智能体） 通常指围绕任务持续判断与行动的系统；源码同名对象还可能专指运行句柄，必须看语境。
Agent Loop（智能体循环驱动） 组织一次次请求与结果的值班流程，不是模型本身。
Tool（工具） 可请求的动作与执行路径，像扳手；是否执行还受策略与参数影响。
Skill（技能指令） 可复用的做事方法，像排查手册；手册不替代工具和权限。
Session（会话） 记录工作经过的日志及相关状态，不等于每次全量送给模型。
Sandbox（沙箱） 约束执行影响范围的机制；护栏并不等于绝对安全。

别让比喻越界

工单不是线程，通讯录不是模型的记忆，房间不是安全沙箱，图上的阅读箭头也不自动等于源码调用。遇到行为判断，回逐步讲解检查实现与异常分支。
