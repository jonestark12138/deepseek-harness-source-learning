一、先从熟悉的排障现场开始

第五讲确认会话记录怎样成为后续模型请求的材料。现在把镜头移到任务开始以前：日志、文件工具与模型能力分属不同插件，它们究竟怎样被装进同一应用？

同一份代码，在网页模式和后台模式下会装出不同应用。你在某处写了配置，启动后却发现值不对；或者配置已经打印出来，插件还是没有工作。

Java 工程师常会先查“到底选了哪个 Profile（装配方案）”“配置源谁覆盖谁”“受容器管理的对象有没有创建”。这个排查方向可以带过来，但这里的装配方案有具体文件结构，不能直接当成 Spring 的环境名称。

我们把问题分成两次核对：纸上最终要装什么？这些设备实际能不能工作？ 前一次查配置，后一次查依赖和启动结果。混在一起查，容易反复修改正确的文件，却始终找不到失败环节。

二、四个角色：方案、套装、修改单、安装员

方案像车间选装单，决定选哪几套设备。Bundle（插件套装）是带配置与代码的分发单元。Patch（配置补丁）是对装配配置的修改指令。Loader（装配器）负责把Entry（配置条目）接入插件系统。

本图：左侧是装配依据，右侧是安装动作。起重吊机是装配器的比喻，不是操作系统线程。

看入口 bin.ts（命令行入口文件），它先解析命令，再在装配方案分支调用 runProfile()。传入的四项分别是环境快照、方案名、补丁文件列表、交给应用的参数。插件管理和配置打印是另外的分支，不必都启动整棵应用树。

随后，loadProfile()（方案读取函数） 读取方案的 package.json，看 dsh.profile.bundles 数组。下面是便于辨认结构的教学示例，使用本仓库已有的套装名称：

{
  "dsh": {
    "profile": {
      "bundles": [
        "@deepseek-ai/dsh-base",
        "@deepseek-ai/dsh-web-app"
      ]
    }
  }
}

数组表达套装层的应用顺序。每个套装自己的清单再用 dsh.bundle.patch 指出补丁文件。例如基础套装提供 cordis.patch.yml，在里面用 insert 插入模型、会话、工具等配置行。

这里出现第五个词：配置行（配置条目），就是“要安装哪个插件、给它什么配置、是否禁用”等信息组成的一项记录。id 是该行的定位编号，name 通常是加载模块的名称。它们不等于插件运行实例。

为什么根配置竟然是空数组？

prepareProfile()（方案准备函数） 每次把方案目录里的 cordis.yml 写回 []。这不矛盾：场地先清空，设备由后面的套装和补丁插入。

文件存在还给加载流程一个目录锚点，便于解析相对路径。源码注释解释了重写原因：装配器的写回可能把已经组合的行留在根文件里；下次再应用套装 insert（插入配置行），就会重复插入。根配置是起点，最终配置是计算结果。 因此日常调整应进入相应补丁文件，而不是把这份空根文件当总配置去维护。

三、同一行被改了几次，谁最后说了算？

先看全貌，再看函数。把补丁想成轮流批改同一张装配清单：套装给初稿，方案做专项调整，本机偏好再改，本次命令还可以追加修改。

本图：阶梯表示补丁应用次序；它不表示设备依次开机。图把源码最后一组展开成两种来源。

allPatches()（补丁排序函数） 是最短的顺序证据：

return [
  ...composed.bundlePatches,
  ...composed.profile.patches,
  ...composed.homePatches,
  ...composed.overlays,
]

只关注数组展开的先后。套装按方案列出的顺序展开；之后是方案自己的 cordis.patch.yml；再是运行支撑系统主目录中的同名补丁；最后是叠加层（追加覆盖层），包括按参数顺序读取的 --patch 文件。

“主目录”在这里指由 resolveDshHome() 解析的运行支撑系统数据目录，不是当前仓库目录。方案补丁只影响这个方案，本机补丁影响经过该启动入口的各个方案。

composeProfile()（方案组合函数） 还可能在追加覆盖层最后加一条遥测禁用补丁：相关环境变量非空，并且配置里确有遥测行时，追加 disabled: true。所以“命令行永远最高优先级”不够准确。也不要据此扩展成所有环境变量都能覆盖所有 YAML（配置数据格式）字段；这里只核对了这一项显式逻辑。

现在可以回答开头的第一种故障：方案文件看起来改对了，但用户数据层或本次 Overlay（追加覆盖层）又写了同一字段，最后生效的值就可能不同。

四、最容易踩坑的地方：改的是哪一层？

“后写覆盖前写”还少了一个关键细节：覆盖粒度。

applyEntryPatches()（配置行补丁算法） 先复制输入并按行定位编号建索引，然后依次处理补丁。insert 添加新行，普通补丁用 id 找到旧行。真正修改的核心只有几行：

for (const [key, value] of Object.entries(overrides)) {
  if (key === 'id') continue
  target[key] = value
}

这是配置条目顶层赋值。如果键是 disabled，改的是禁用标记；如果键是 config，换的就是整个配置对象。

本图：“换页”对应整份配置对象替换。没有画成在旧页上补一小行，因为那会暗示深合并。

下面用一个虚构插件做纸面实验。字段只为展示补丁算法，不属于项目某个真实插件：

# 第一层：插入设备配置
- insert:
    - id: demo
      name: demo-plugin
      config:
        directory: reports
        timeout: 30

第二层：

- id: demo
  config:
    timeout: 60

两层应用后，demo（教学示例行） 行的配置对象是 { timeout: 60 }，没有 directory（目录字段）。旧页整张换掉了。若希望保留目录，第二层就要明确写上它。之后某插件是否通过自己的配置解析补默认目录，是另一个阶段，不能说补丁算法保留了旧值。

再做三个小判断：

改法 此阶段结果 为什么
只写 disabled: true 原配置对象保留 没覆盖配置对象字段
指向不存在的定位编号 告警并跳过该补丁 查不到修改对象
定位编号命中，但给了不同的名称 告警并跳过 名称在这里是目标匹配护栏，不是重命名指令

插入行会立即加入索引，因此后面的补丁可以修改前面刚插入的行。这一点由配置组合测试交叉验证。不要把所有无效补丁都想成“启动立即失败”：未命中定位编号的情况在这个函数里是告警并跳过。

五、纸面装好了，运行为什么还可能失败？

前面处理的全是配置数据。现在才轮到安装员。

boot() 先建立根插件上下文，也就是服务查找与局部信息的入口，再装配加载机制。这里还不需要先读第六讲：把上下文理解成工作台的通讯录即可。配置文件入口负责读配置文件并应用补丁，装配器把配置条目连接到 Cordis 的插件安装过程。一个配置行可能对应一个插件，也可能是承载子树的分组或文件入口。

把boot()（启动与验收函数） 的主体按职责读，可以看到：

  1. 建根插件上下文，设置路径等宿主信息。
  2. 安装装配器。
  3. 执行宿主准备回调 prepare，让环境与命令行服务先可用。
  4. 挂载根 Include（配置文件入口），进入配置树装配。
  5. 等待加载树收敛，再检查启用行是否真正激活。

“收敛”先理解成：这一轮正在推进的装配处理告一段落。它本身不等于所有启用插件都成功，所以后面还有激活审计。

图 4：未连接与已连接是依赖条件的比喻。缺少必需服务时不会凭空激活，正常存活的启动树会由审计报告失败。

插件的每次安装都有一个运行实例，源码称为 Fiber（插件安装实例）；它根据声明的必需服务决定能否加载。第六、七讲将继续拆开这项机制。设备已经送到门口，但电源没接好，不能算验收通过。

assertEntriesActivated()（激活审计） 把问题进一步分开：模块没能加载出来；插件初始化失败；或者插件仍在等待某个服务。disabled（禁用标记）行不参加“必须可用”的要求。初始化失败会保留相关错误信息，缺依赖则列出等待的服务名。

boot() 捕获启动异常后会释放根插件安装实例，回收已经装上的部分，再包装错误抛出。因此不能把启动器画成“碰到坏设备仍一路前进，最后总会返回成功”。

还有一个源码中的特殊情况：某个一次性应用在启动窗口内主动完成并释放整棵树，装配器已不存在时会提前返回。它不是“仍存活的树通过了激活审计”。正常运行与主动结束要按实际分支区分。

为什么不能按 YAML（配置数据格式）行顺序推断激活顺序？

基础套装注释已明确提醒：行顺序不携带加载语义，激活取决于服务可用性。更底层的依据在 Fiber._refresh()（安装实例的依赖刷新方法），它检查注入的服务实现，决定进入加载还是卸载。

配置应用像改清单，依赖激活像接好电才允许开机。这两条顺序解决不同问题。

六、改完文件，为什么有时要重新启动？

方案的 patchReload 决定本次运行怎样对待用户补丁变化。live 表示运行中监听并重新组合；startup 表示启动时应用，本次运行不安装这条监听路径。

这不表示仅启动时应用模式忽略用户配置。两种模式都先应用用户层，差别在启动以后是否跟随修改。runProfile()（方案启动函数） 后半段明确用条件分支安装监听与提交就绪通知。

这是本讲与“热更新”之间的边界。你只需要知道到哪里查，不必现在就读完事务回滚和文件监听。

练习与答案

第九讲练习 · 先改清单，再判断能否开工

先独立回答，再展开。所有源码位置绑定本讲快照；虚构配置仅用于理解算法。

1. 空文件真的什么都没装吗？

方案目录的 cordis.yml（根配置文件） 只有 []，能否判断它没有模型和工具？

展开答案

不能。它是空根配置，套装的 insert（插入配置行）和后续补丁构成最终行列表。去看 prepareProfile（准备方案目录的函数）、loadProfile（方案读取函数） 和 allPatches（补丁排序函数），而不是只看根文件。证据。

2. 手算整体替换

初始 demo.config（示例行配置）是 { directory: 'reports', timeout: 30 }。方案层只把配置对象写成 { timeout: 60 }。本机层只写 disabled: true。最后配置对象与 disabled（禁用标记）各是什么？

展开答案

配置对象为 { timeout: 60 }，disabled（禁用标记）为 true（真值）。directory（目录字段）在方案层整体替换时丢失；本机层没写配置对象，不会再改它。这里说的是补丁组合结果，不是插件补默认值后的结果。证据。

3. “后写”就一定成功吗？

先写 { id: 'missing', disabled: true }，但前面从未插入 missing（不存在的示例编号） 行，会怎样？再给已存在行指定不同名称呢？

展开答案

两种情况都会告警并跳过该补丁；不会因此自动新建行，也不是重命名。新建用 insert（插入配置行）。证据。

4. 是同一条顺序吗？

A 插件行写在 B 前面，但 A 必需的服务由 B 提供。能否要求 A 先 ACTIVE（已激活状态）？

展开答案

不能。配置行顺序与依赖激活顺序不同。A 必须等相应服务满足后才可能完成加载；把 A 的行向上移动不能消除依赖。证据。

5. 启用插件缺服务，启动与验收会当作成功吗？

限定：应用没有主动提前退出，启动树仍然存活。

展开答案

不会。等待树收敛之后还会审计启用行。等待依赖行会报告缺少的服务；启动与验收捕获失败后释放根插件安装实例，再抛出带上下文的错误。证据。

6. 画回缺失的一步

用清单、吊机、模块、插座、状态灯画“已配置但未激活”。写出一条箭头的具体含义，并说明这不是线程调度图。

展开一种参考摆法

清单交给吊机，表示按配置挂载；模块旁留一个未连接的插座，表示必需服务未满足；等待灯标注等待依赖。若只把模块画在台上，却直接亮就绪灯，就漏掉了加载和激活验证。

7. 把 Java 经验用对

这套装配方案和 Spring 装配方案相似在哪里，不能等同在哪里？

展开答案

相似的是不同方案会影响应用装配。这里的具体机制是方案包清单选 bundles（套装名称数组），多层配置补丁改配置条目，然后由装配器与 Cordis 安装和激活；不能把它简化成选择一组环境变量，也不能照搬 Spring 配置深合并规则。证据。

8. 源码寻宝与预测

找到命令行补丁之上的条件性调整。如果 patchReload（补丁重载模式） 是仅启动时应用，用户补丁会被忽略吗？

展开答案

条件性调整是 composeProfile（方案组合函数） 可能追加的遥测禁用补丁。仅启动时应用仍在启动时应用方案与本机用户补丁，只是不在本次运行中安装运行中更新监听。证据。

英文与中文 直觉、实际职责与边界
Profile（装配方案） 选择套装并做调整的选装单，不只是某个环境名称。

Loader（装配器） 把配置树接入插件安装与管理的机制，像安装员。

boot（启动与验收） 建立应用、装配并检查运行条件，不只是读完配置文件。
Include（配置文件入口） 把文件中的配置与补丁接进装配树。
