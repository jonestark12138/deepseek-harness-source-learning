逐步讲解

第15讲 · 记录员、审批者和执行者，谁必须等待谁

源码基线：cd5ef8148158c3a752a658978873241fdf8e2bbc。业务案例为虚构 Java 运费服务；图与流程是教学推演，源码事实另有固定证据。

一、同一运费任务遇到的下一道障碍

第十四讲终于让读取和测试指向同一工作区。现在报告到达时要更新界面，持久化可能要等待，修改请求又必须让审批者裁决。它们不能全用同一种“发事件”处理。否则可能在审批未完成时继续动作，或者因为统计监听器出错连必要通知都没收到。本讲沿这些不同责任，选择正确的协作契约。

三格为同一运费任务的教学状态变化或故障对照。图不是实际运行日志；关键区别见各格说明。

二、只发通知，不等工作完成

假设报告到达后，两个观察者分别更新界面和发送异步统计。若主流程不需要它们的结果，可以考虑 emit（同步通知，不等待异步结果）。

通知实现 同步遍历并调用监听器。监听器若返回异步结果凭据，这里不等待它。可以想成逐个按响门铃，不站在门口等每个人办完事情。

有两个不能省略的边界。第一，异步工作被启动后可能重叠，不能因为“同步遍历”就说这些工作绝不并发。第二，如果前一个监听器直接同步抛错，遍历会被打断，后面的监听器可能没有被调用。这个方法没有为每个监听器做异常隔离。

因此“全部通知成功”和“全部事情完成”都不能从函数名推出来。如果后续必须依赖工作完成，就要换一种契约。

三、需要所有人交卷，就等待全部结果

parallel（并行发起并等待全部完成）适合彼此独立、但后续需要一起等完的任务。像把两份检查单分别交给两个人，然后等两人都交卷。

并行实现 等待所有监听器成功或失败，再统一检查结果；若存在失败，抛出 AggregateError（汇总错误）。一个人交了失败卷，不表示其他人的工作自动取消。

这里的并行指异步任务可以共同推进，不保证每个监听器分配一条线程，也不能让耗时同步计算凭空并行。不要把 Java 线程池的执行模型直接套过来。

四、只需要一个裁决，为什么还分两种模式

有些问题不是“所有人做完”，而是“找到第一个明确结论就停”。例如逐个询问处理者有没有意见。bail（同步遇到结论就停）与 serial（逐个等待裁决）共享停止值规则，但等待方式不同：后者会先等待当前处理者的异步结果，再决定要不要问下一位。

停止值判定 将 null、false、undefined 视为还没有结论，其他值都能停止。因此 0 和空字符串也能停止；不能把规则记成“真值才停止”。

看 两种遍历实现：同步版本直接检查返回对象；逐个等待版本先等到异步最终值，再做判定。

做一个思想实验：首个监听器返回 Promise.resolve(false)。同步版本拿到的是一个对象，因此立刻停止；逐个等待版本拿到最终的 false，因此继续。两种模式停止的不是同一个层次上的“值”。这也是补课 A异步知识在真实源码中的用处。

五、需要“进门前检查、出门后处理”，怎么办

前面的几种模式由分发器控制遍历。另一种场景是：处理者需要决定要不要把请求交给后面的人，并且还想加工返回结果。waterfall（包裹式接力链）在本项目中就承担这个角色。

next（继续后续处理的函数）像门卫手里的放行权。下面是教学示例，事件名和辅助函数为便于讲解而虚构：

ctx.on('request', async (input, next) => {
  validate(input)
  const result = await next()
  return audit(result)
})

进入时先校验；调用继续函数后，把控制交给剩余队列；结果回来再审计。也可以不调用继续函数而直接返回，此时后面的监听器和默认处理都不会执行。它很像拦截器的前置与后置处理，但具体参数契约要读这个项目，不能照搬别的框架。

接力链源码 用队列依次取出下一项。这里的继续函数不接收替换参数，因此不能写成 next(newInput) 并声称它会把新参数传给下一层。闭包中的参数才是这条实现实际使用的参数。

这一点修正了旧稿中的错误说法：本实现不是预先从后往前包装监听器，也没有通过继续函数替换参数的接口。可以讲“逐层进入、逐层返回”的可观察过程，但不能借别的中间件实现来补不存在的机制。

5.1 给接力链记一条可复核的调用轨迹

本书使用两个监听者和默认处理，实际运行得到：甲进入 → 乙进入 → 默认返回 7 → 乙退出 → 甲退出。甲和乙都必须等待继续函数的结果，才能把后置工作放在返回之后；只写调用却不等待，就不能宣称“后置审计发生在内部工作完成后”。

再在最外层加一个直接返回拒绝的处理者，轨迹只剩“否决”。这不是请求已经执行之后再改标签，而是后续从未取得控制权。这个反例能检查实际授权链是否把裁决放在动作前。

还有一个容易误用的细节：此处队列由闭包取下一个监听者；继续函数不是可以任意多次重试的业务入口。不要把两次调用当成“重试整个链”，也不要依靠没有声明的单次调用防护。需要重试时，应在明确边界上设计次数、错误类别和幂等责任。

5.2 三个小实验把等待方式真正分开

在真实上游函数上，首监听者返回最终为 false 的异步结果：同步裁决看见的是结果凭据对象，因此停止；逐个等待先取到最终值，继续问第二位并得到明确结论。再把并行通知的一位改为立即失败、另一位挂在受控等待门上；关闭等待门之前，整体仍不能结束。另一位最后完成，才汇总失败，没有自动取消它。

这三种轨迹在不同输入下相似、在边界下不同。只看成功日志，可能把所有模式误以为“都是调几个回调”；故障注入让等待与停止规则可观察。完整实验与断言在本讲练习页，可独立重复。

六、真实案例：谁来向用户追问缺失信息

回到测试排查。如果缺少复现条件，系统可能需要询问用户。负责发问的服务不该写死当前一定是网页界面。

问题事件的类型契约 说明请求和继续处理的形式。发问实现 把“没有回答者”的函数放在链尾。

作用域中某个处理者能回答，就返回结果；不负责，就交给后面。所有处理者都放行后，链尾抛出 NO_PROVIDER（没有可用回答者）。这不是默认成功，也不是模型已经得到用户同意。它只是一次提问没有找到承接方的明确失败。

第十四讲的服务解决“找到提问入口”；本讲的接力链解决“提问由哪个参与者承接”。二者不是互相替代的两套名词，而是在同一任务的不同位置分工。

七、用一张契约表选路，再回源码核对

调用方式 等待什么 谁决定停止 本讲的直觉
emit（通知） 不等监听器的异步结果 同步异常仍可中断遍历 按门铃
parallel（并行等待） 所有监听器的最终结果 全部完成后汇总错误 等所有人交卷
bail（同步裁决） 不展开异步凭据 首个停止值 当场要答复
serial（逐个等待裁决） 当前监听器的最终值 首个最终停止值 等这人答完再问下一人
waterfall（包裹式接力） 由接力链返回值决定 当前处理者是否继续 门卫放行与回程处理

表里的顺序是比较顺序，不是一次任务依次经过五种模式。实际读源码时，先找事件类型，再找采用哪种分发方法，最后找监听者；缺任何一站都不能还原协作契约。

首个监听者返回最终为假值的异步对象时，同步裁决与逐个等待是否等价？并行等待中的失败会自动取消其他人吗？

推演答案

不等价：同步模式停在对象上，等待模式取得假值后继续。并行等待全部收束后汇总错误，不自动取消其他监听者。

词典用于回查，正文在首次使用处解释。代码、参数与路径保留原拼写；产品名称不逐字翻译。模型上下文和插件上下文不是一回事。

emit（同步通知，不等待异步结果）

逐个同步调用通知监听器，不等待它们返回的异步结果，像依次按门铃。同步抛错可中断后续通知，不代表所有人都已办完事。

parallel（并行发起并等待全部完成）

发起多个监听任务并等待全部最终结果，像等两位检查者都交卷。异步并发不等于每项一条线程；一个失败不自动取消其余任务。

AggregateError（汇总错误）

把多个失败一起表达的汇总错误，像把检查者的失败卷放进同一个档案袋。它保留多个原因，不表示此前操作都被回滚。

bail（同步遇到结论就停）

同步遇到停止值就结束的裁决模式，像当场要一个结论。本实现只有空值、布尔假值和未定义值不停止，异步凭据对象本身会使它停止。

serial（逐个等待裁决）

先等当前处理者给出最终结果，再决定是否询问下一位，像逐位等待审批者答复。与同步裁决相比，它先展开异步结果凭据；拿到布尔假值仍继续，而不是把凭据对象当结论。

waterfall（包裹式接力链）

由当前处理者决定是否继续、并可处理返回结果的包裹式接力链，像进门检查与回程审计。本项目按队列推进，继续函数不接收替换参数。

next（继续后续处理的函数）

继续执行剩余处理链的函数，像门卫放行。当前处理者不调用它，后续链就不执行；本实现不能靠传新参数替换链的输入。
