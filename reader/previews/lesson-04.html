逐步讲解

第四讲逐步讲解 · 别把三张地图叠成一团线

源码快照：cd5ef8148158c3a752a658978873241fdf8e2bbc。

如果把多包单仓库想成“一大堆代码包放在一个 Git（版本管理工具）仓库”，你只看到了围墙。真正决定工程如何工作的是几份用途不同的地图。

一、第一张图：谁属于包管理工作区

先从园区名册找到会话包，不急着画所有关系。

pnpm-workspace.yaml#L1-L17 列出工作区成员路径，例如 vendor/*、packages/*/* 和 apps/*。这些模式像园区名册：说明哪些目录参加统一的包管理，不表示成员之间全都有依赖。

读者无需记住包的总数。先拿会话包做例子：它的目录符合成员路径，目录中又有包清单，因此属于这份名册。接下来仍要看清单声明的依赖，才能知道它和谁协作。

linkWorkspacePackages: true 允许满足依赖要求的本地工作区包参与链接；名称相同还要符合版本等解析条件。“住在同一园区”仍不表示两个包一定相依。

二、第二张图：TypeScript 怎样检查关系

名册只管成员。成员之间怎样参加类型检查，要换第二份文件，不能沿着名册猜。

根 tsconfig.json#L1-L14 是一个聚合检查配置：

{
  "files": [],
  "references": [
    { "path": "./tsconfig.host.json" },
    { "path": "./tsconfig.client.json" }
  ]
}

files: [] 很关键：根项目不把全仓库源码硬塞进一个 TypeScript 类型检查单元，而是把工作交给宿主侧与客户端侧两个聚合检查单元。

这里的 references 像施工前置关系。TypeScript 需要知道当前项目引用了哪些项目以及它们的类型产物边界。它不表示 A 在运行时一定调用 B，更不表示两个服务通过网络通信。

三、第三张图：运行文件怎样出货

类型检查通过只是质检结果。要得到可运行文件，还要找到负责加工与出货的build（构建）配置。

tsdown.config.ts#L10-L29 又是另一张图。它选择普通包管理工作区构建范围、入口模式、lib 输出目录、标准模块机制格式和宿主侧 Typert（本项目宿主构建中的类型相关插件）插件。

于是同一个 package（代码包）至少可能出现在三种关系里：

问题 去哪看 箭头表示什么
它属于本仓库的包管理工作区吗 pnpm-workspace.yaml 成员归属
类型检查前要看哪些项目 tsconfig*.json 项目引用 TypeScript 项目引用
怎样得到运行时文件 根脚本、tsdown（构建打包工具）、包内配置 构建调度与产物

读图时先问“这条箭头的动词是什么”，比盯着箭头方向更重要。

四、根构建：从按钮追到调度员

知道出货配置以后，接着问谁实际调度这些步骤，以及失败怎样阻止后续步骤。

根 package.json#L19-L25 写着：

"build": "tsx scripts/build.ts",
"build:lib": "npm run build:lib:host && npm run build:lib:client",
"build:web": "pnpm --filter @deepseek-ai/dsh-web-frontend run build"

这像控制台上的三个按钮。要知道总按钮按下后做什么，继续读 scripts/build.ts#L31-L49：

  1. 解析 client（客户端侧）构建装配方案与环境；
  2. 删除旧构建记录；
  3. 调用 build:lib；
  4. 调用 build:web；
  5. 写入新的客户端侧构建记录，并报告产物数量。

注意 runScript() 会检查子进程退出状态；任何子脚本非零退出都会使总构建失败。这才是“构建顺序”的实现证据，不是脚本名字带来的想象。

五、为什么宿主侧与客户端侧要分开

总调度把任务交下去，但为什么还分宿主和客户端？第三讲看到的共同接口扩展在这里带来了检查边界问题。

tsconfig.client.json#L1-L14 的注释直接说明：宿主侧与客户端侧都会给 Cordis Context 的同名键合并声明，但对应服务不同；若放进同一个类型检查单元，两个世界会在类型层面撞车。

所以根聚合检查配置把它们分开。共享的会话、大语言模型、工具服务等叶子项目可以被两边引用，但各自的插件上下文的类型扩展保持在自己的检查单元里。

两份聚合配置都写 noEmit: true。可把它理解成“总质检站只检查，不从这里直接装箱”；真正产物仍由代码包编译和 tsdown（构建打包工具）等构建步骤生成。

六、落到一间工坊：会话代码包的接线单

三种地图已经分清，现在把镜头缩到会话包，为第五讲读实现做准备。

packages/core/session/tsconfig.json#L1-L32 很短，却能回答四个问题：

  • rootDir: src：源码从哪里进入；
  • outDir: lib/types：TypeScript 产物边界在哪里；
  • include: ["src"]：本项目检查哪些自身文件；
  • references：它在类型项目图中依赖 cordis（插件框架包）、品牌标识、大语言模型、服务可见范围等七个项目。

这还没告诉你会话做什么业务，只帮你定位它在构建与类型网络中的位置。下一讲才用一套固定方法拆读这个代码包。

七、五站源码路线

  1. pnpm-workspace.yaml：只回答成员边界。
  2. 根 package.json 脚本：找到构建入口名。
  3. scripts/build.ts：确认真实顺序与失败传播。
  4. tsconfig.json、tsconfig.host.json、tsconfig.client.json：辨认类型检查图。
  5. packages/core/session/tsconfig.json：把全景落到一个节点。

八、一句话总结

monorepo（多包单仓库）是园区，包管理工作区清单圈成员，project references（类型项目引用）组织类型检查，构建脚本与 tsdown（构建打包工具）生成运行产物。先分清地图的用途，再追一条真实脚本链，就不会被几百个代码包和几千条线吓住。

不是。成员归属只说明参加统一包管理。依赖声明、源码导入与实际调用需要分别核对。

2. 类型通过能直接上线吗？

展开答案与理由

不能。质检与出货是不同步骤。还需追构建脚本、产物与实际运行验证。

3. 同名栏目为什么冲突

宿主和客户端都扩展插件上下文，为什么分开检查？

展开答案与理由

同名服务栏目可能对应不同契约，合进同一类型检查单元会冲突。分开检查不是说它们完全不共享代码。

4. 构建按钮该怎么追

根脚本的名字叫构建，是否已经证明所有子步骤会执行？

展开答案与理由

没有。继续读实际调度器，核对调用顺序和非零退出后的失败传播。名字只给入口，不给行为证明。

术语词典

第4讲术语与比喻词典

遇到陌生词，先回到这个问题：几百个包放在一起，怎样找到会话包又不把三种关系混淆？ 以下是查阅页，正文会在需要时解释关键概念。英文只用于和源码对照；它不是额外的背诵任务。

英文与中文 直觉、实际职责与边界
monorepo（多包单仓库） 同一代码仓库管理多个包，像园区里有多间工坊；不是所有包都相互依赖。
workspace（包管理工作区） 包管理器按名册识别的一组本地包；不是智能体任务的工作空间概念。
package（代码包） 有身份、入口和依赖约定的组织单元，不必对应一个独立进程。
project references（类型项目引用） 告诉类型检查器项目之间的边界，不是运行时函数调用图。
host（宿主侧） 承载应用运行能力的一侧，和浏览器界面侧分开理解。
client（客户端侧） 界面等客户端代码所在的一侧，可能有自己的服务类型。
build（构建） 把源码加工为检查结果和可运行产物的流程，不等于启动所有插件。

别让比喻越界

工单不是线程，通讯录不是模型的记忆，房间不是安全沙箱，图上的阅读箭头也不自动等于源码调用。遇到行为判断，回逐步讲解检查实现与异常分支。
