第四讲 · 走进 264 间工坊的工业园

源码快照：cd5ef8148158c3a752a658978873241fdf8e2bbc。旧计划里的“254 个 package”已经过期；按本提交的 workspace glob 实测是 264 个。

这一讲只追一个问题：这么多 package，究竟怎样成为一个可检查、可构建的系统？

主比喻是一座工业园。园区目录回答“谁住在这里”，施工依赖图回答“质检前要先看谁”，出货路线回答“哪些文件怎样变成运行产物”。三张图都画 package，却绝不是一张图。

完成标准

  1. 说出 264 的复核口径，并知道它只绑定本次提交。
  2. 区分 workspace 成员图、TypeScript project-reference 图、运行时产物图。
  3. 从根 build 追到 build:lib、build:web 和构建记录。
  4. 解释 host/client 分开是类型可见性隔离，不是两个仓库。
  5. 打开任一 package 的 tsconfig，读出源码目录、类型输出目录和 project references。

视觉课件

第四讲视觉课件 · 同一座园区，三张不同地图

1. Workspace 先圈出谁属于园区

264 是把固定提交中的 glob 展开后，统计含 package.json 的成员。它不是永恒常数，也不含根 package。

2. 园区目录、施工图、出货图不能混用

“在一个 workspace”不等于“运行时互相调用”；references 也不等于网络请求或进程通信。

3. 根 build 像总调度员

package.json 只给出按钮标签，真正顺序要到 scripts/build.ts 中确认。

4. Host 与 Client 是两条质检车道

两个聚合项目都 noEmit：它们的核心工作是检查，不是直接出货。

5. 单个 package 有自己的接线单

从全景落到一个节点，先读 rootDir、outDir、include、references，不要一上来钻进数千行实现。

逐步讲解

第四讲逐步讲解 · 别把三张地图叠成一团线

源码快照：cd5ef8148158c3a752a658978873241fdf8e2bbc。

如果把 monorepo 想成“一大堆 package 放在一个 Git 仓库”，你只看到了围墙。真正决定工程如何工作的是几份用途不同的地图。

一、第一张图：谁属于 workspace

pnpm-workspace.yaml#L1-L17 列出六组路径：

  • vendor/*：9 个；
  • packages/*/*：247 个；
  • apps/*：2 个；
  • native/landlock-run 及其 packages/*：4 个；
  • python/sdk-runtime：1 个；
  • website：1 个。

合计 264。统计口径是：在固定提交中展开这些 glob，只计算实际含 package.json 的目录，不把根 package.json 自己算进去。

旧规划写 254，为什么这里必须改？因为成员数是快照事实，不是项目名称的一部分。源码学习材料若不固定 commit 和复核口径，很快就会把昨天的正确数字讲成今天的错误事实。

linkWorkspacePackages: true 让匹配名称的本地包优先链接到 workspace 源；但“住在同一园区”仍不表示两个包一定相依。

二、第二张图：TypeScript 怎样检查关系

根 tsconfig.json#L1-L14 是一个 solution file：

{
  "files": [],
  "references": [
    { "path": "./tsconfig.host.json" },
    { "path": "./tsconfig.client.json" }
  ]
}

files: [] 很关键：根项目不把全仓库源码硬塞进一个 TypeScript program，而是把工作交给 host/client 两个聚合检查单元。

这里的 references 像施工前置关系。TypeScript 需要知道当前项目引用了哪些项目以及它们的类型产物边界。它不表示 A 在运行时一定调用 B，更不表示两个服务通过网络通信。

三、第三张图：运行文件怎样出货

tsdown.config.ts#L10-L29 又是另一张图。它选择普通 workspace 构建范围、入口模式、lib 输出目录、ESM 格式和 host 侧 Typert 插件。

于是同一个 package 至少可能出现在三种关系里：

问题 去哪看 箭头表示什么
它属于本仓库的 workspace 吗 pnpm-workspace.yaml 成员归属
类型检查前要看哪些项目 tsconfig*.json references TypeScript 项目引用
怎样得到运行时文件 根脚本、tsdown、package-local config 构建调度与产物

读图时先问“这条箭头的动词是什么”，比盯着箭头方向更重要。

四、根 build：从按钮追到调度员

根 package.json#L19-L25 写着：

"build": "tsx scripts/build.ts",
"build:lib": "npm run build:lib:host && npm run build:lib:client",
"build:web": "pnpm --filter @deepseek-ai/dsh-web-frontend run build"

这像控制台上的三个按钮。要知道总按钮按下后做什么，继续读 scripts/build.ts#L31-L49：

  1. 解析 client build profile 与环境；
  2. 删除旧构建记录；
  3. 调用 build:lib；
  4. 调用 build:web；
  5. 写入新的 client build record，并报告产物数量。

注意 runScript() 会检查子进程退出状态；任何子脚本非零退出都会使总构建失败。这才是“build 顺序”的实现证据，不是脚本名字带来的想象。

五、为什么 host/client 要分开

tsconfig.client.json#L1-L14 的注释直接说明：host 与 client 都会给 Cordis Context 的同名 key 合并声明，但对应服务不同；若放进同一个 program，两个世界会在类型层面撞车。

所以根 solution 把它们分开。共享的 session、llm、tools 等叶子项目可以被两边引用，但各自的 Context 扩展保持在自己的检查单元里。

两份聚合配置都写 noEmit: true。可把它理解成“总质检站只检查，不从这里直接装箱”；真正产物仍由 package 编译和 tsdown 等构建步骤生成。

六、落到一间工坊：Session package 的接线单

packages/core/session/tsconfig.json#L1-L32 很短，却能回答四个问题：

  • rootDir: src：源码从哪里进入；
  • outDir: lib/types：TypeScript 产物边界在哪里；
  • include: ["src"]：本项目检查哪些自身文件；
  • references：它在类型项目图中依赖 cordis、brand、llm、scope 等七个项目。

这还没告诉你 Session 做什么业务，只帮你定位它在构建与类型网络中的位置。下一讲才用一套固定方法拆读这个 package。

七、五站源码路线

  1. pnpm-workspace.yaml：只回答成员边界。
  2. 根 package.json scripts：找到构建入口名。
  3. scripts/build.ts：确认真实顺序与失败传播。
  4. tsconfig.json、tsconfig.host.json、tsconfig.client.json：辨认类型检查图。
  5. packages/core/session/tsconfig.json：把全景落到一个节点。

八、一句话总结

Monorepo 是园区，workspace 清单圈成员，project references 组织类型检查，构建脚本与 tsdown 生成运行产物。先分清地图的用途，再追一条真实脚本链，就不会被几百个 package 和几千条线吓住。

练习与答案

第四讲练习与答案

练习 1：264 是什么数字

判断：“DeepSeek Harness 永远有 264 个 package。”

展开答案

错误。264 是固定提交 cd5ef814… 中展开 pnpm-workspace.yaml 路径后，命中含 package.json 目录的数量。换提交后必须重新统计。

练习 2：成员关系是不是调用关系

两个 package 都匹配 packages/*/*，能否推出 A 会在运行时调用 B？

展开答案

不能。只能确认二者都是 workspace 成员。运行时调用要继续看 import、依赖声明、实现或追踪证据。

练习 3：追根 build

根 npm run build 的可观察顺序是什么？

展开答案

进入 scripts/build.ts，解析构建环境，删除旧记录，运行 build:lib，再运行 build:web，最后写新构建记录。任何子脚本非零退出会让总构建失败。

练习 4：noEmit 的误区

判断：“host/client tsconfig 都 noEmit，所以仓库不会生成 JavaScript。”

展开答案

错误。它只说明这两个聚合检查项目本身不发出文件。package 构建、tsdown 和 Web 构建仍负责生成运行产物。

练习 5：为什么不合成一个 program

展开答案

host/client 会给 Cordis Context 的相同 key 合并不同服务声明。放进同一个 TypeScript program 会让两个类型世界碰撞，因此用两个聚合项目隔离；共享叶子项目仍可被两边引用。

练习 6：给箭头命名

看到 packages/core/session/tsconfig.json 引用 packages/llm/llm，最稳妥的表述是什么？

展开答案

“Session TypeScript 项目引用 LLM TypeScript 项目。”不要直接升级成“Session 运行时调用 LLM”；要证明后者还需看 manifest、值 import 与调用实现。

分享稿

第四讲分享稿 · 一座园区需要三张地图

DeepSeek Harness 固定源码快照里有 264 个 workspace package。这个数字不是背诵题，而是一次证据训练：它来自展开 workspace glob，换提交就要重算。

我会把 monorepo 比作工业园。第一张园区目录来自 pnpm-workspace.yaml，只说明谁是成员；第二张施工依赖图来自 TypeScript project references，说明类型检查项目如何连接；第三张出货图来自根构建脚本、tsdown 和 package-local 配置，说明怎样产生运行文件。

根 build 不是一个神秘黑盒。package.json 把它指向 scripts/build.ts，实现先清旧记录，再跑 library、Web，最后写构建记录。

Host 与 Client 分成两条检查车道，是因为它们给同一个 Cordis Context key 合并不同服务声明；共享叶子仍可复用。两个聚合 tsconfig 的 noEmit 表示总质检站只检查，不表示整个仓库不出 JavaScript。

面对几百个 package，不要画全量蜘蛛网。先问当前看的是哪张地图，再从根脚本追一条链，最后落到一个 package 的 tsconfig。

术语词典

第四讲术语与比喻词典

英文 / 配置 先这样理解 技术含义 比喻边界
Monorepo 单仓多包 一座工业园 多个相关 package 放在同一版本库协作 不等于一个部署单元
Workspace 园区成员名册 包管理器共同安装、链接和执行脚本的成员集合 不自动形成运行时依赖
Glob 分区圈选规则 用通配模式匹配目录 需要展开后才知道当前数量
Package 一间工坊 有 package manifest 和边界的模块单元 不等于独立进程或微服务
Project reference 施工接线 TypeScript 项目级引用关系 不是运行时调用链
Solution tsconfig 施工总图 无自身源码、聚合子项目的 tsconfig 不直接表示打包策略
Host 后场工作区 Node/本地运行侧的类型与实现面 不等于物理服务器
Client 前场工作区 浏览器/UI 侧的类型与实现面 不等于某一个用户设备
noEmit 只质检不装箱 当前 TypeScript program 不写输出文件 其他构建步骤仍可出产物
Build graph 出货调度图 脚本、工具与产物之间的构建关系 要区分声明与实际执行
tsdown 装箱线 本仓库使用的 TypeScript/ESM 构建工具 不是所有包的唯一构建入口
Artifact 出货成品 构建生成的 JS、网页或记录等文件 不等于源码本身
