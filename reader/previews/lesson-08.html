逐步讲解

第八讲逐步讲解 · 一件事发生后，怎样让多个插件合作？

源码快照：cd5ef8148158c3a752a658978873241fdf8e2bbc。下面的排障故事与简化代码用于教学；准确行为以链接中的分发实现为准。

一、能找到服务以后，还缺一种协作方式

第七讲解决“我要的能力在哪里”。但一次测试排查往往不只是调用一个服务：报告到达时，界面要更新；日志观察者要记录；某一步可能需要等待多个准备任务；如果要向用户追问信息，还得找到愿意回答的界面。

把所有参与者直接写进同一个大函数当然能工作，却会让循环驱动知道太多外围细节。Event（事件）提供另一种组织方式：发起方用约定的事件名和参数表达一次协作，Listener（监听器）登记自己愿意参与的处理。

这里的“事件”不必然是消息队列，也不保证持久化、跨进程投递或失败重试。Cordis 的这一层首先是进程内的调用与分发机制。要理解它，必须继续问：调用后等不等，按什么顺序，谁能让流程停下？

二、只发通知，不等工作完成

假设报告到达后，两个观察者分别更新界面和发送异步统计。若主流程不需要它们的结果，可以考虑 emit（通知分发）（同步发出通知但不等待异步结果）。

通知实现 同步遍历并调用监听器。监听器若返回异步结果凭据，这里不等待它。可以想成逐个按响门铃，不站在门口等每个人办完事情。

有两个不能省略的边界。第一，异步工作被启动后可能重叠，不能因为“同步遍历”就说这些工作绝不并发。第二，如果前一个监听器直接同步抛错，遍历会被打断，后面的监听器可能没有被调用。这个方法没有为每个监听器做异常隔离。

因此“全部通知成功”和“全部事情完成”都不能从函数名推出来。如果后续必须依赖工作完成，就要换一种契约。

三、需要所有人交卷，就等待全部结果

parallel（并行等待）（并行发起并等待全部完成）适合彼此独立、但后续需要一起等完的任务。像把两份检查单分别交给两个人，然后等两人都交卷。

并行实现 等待所有监听器成功或失败，再统一检查结果；若存在失败，抛出 AggregateError（汇总错误）。一个人交了失败卷，不表示其他人的工作自动取消。

这里的并行指异步任务可以共同推进，不保证每个监听器分配一条线程，也不能让耗时同步计算凭空并行。不要把 Java 线程池的执行模型直接套过来。

四、只需要一个裁决，为什么还分两种模式

有些问题不是“所有人做完”，而是“找到第一个明确结论就停”。例如逐个询问处理者有没有意见。同步裁决（bail（同步遇到结论就停））与逐个等待裁决（逐个等待后再判断结论）共享停止值规则，但等待方式不同。

停止值判定 将 null、false、undefined 视为还没有结论，其他值都能停止。因此 0 和空字符串也能停止；不能把规则记成“真值才停止”。

看 两种遍历实现：同步版本直接检查返回对象；逐个等待版本先等到异步最终值，再做判定。

做一个思想实验：首个监听器返回 Promise.resolve(false)。同步版本拿到的是一个对象，因此立刻停止；逐个等待版本拿到最终的 false，因此继续。两种模式停止的不是同一个层次上的“值”。这也是第二讲异步知识在真实源码中的用处。

五、需要“进门前检查、出门后处理”，怎么办

前面的几种模式由分发器控制遍历。另一种场景是：处理者需要决定要不要把请求交给后面的人，并且还想加工返回结果。包裹式接力（可逐层包裹的接力链）在本项目中就承担这个角色。

继续函数（next（继续后续处理）的函数）像门卫手里的放行权。下面是教学示例，事件名和辅助函数为便于讲解而虚构：

ctx.on('request', async (input, next) => {
  validate(input)
  const result = await next()
  return audit(result)
})

进入时先校验；调用继续函数后，把控制交给剩余队列；结果回来再审计。也可以不调用继续函数而直接返回，此时后面的监听器和默认处理都不会执行。它很像拦截器的前置与后置处理，但具体参数契约要读这个项目，不能照搬别的框架。

接力链源码 用队列依次取出下一项。这里的继续函数不接收替换参数，因此不能写成 next(newInput) 并声称它会把新参数传给下一层。闭包中的参数才是这条实现实际使用的参数。

这一点修正了旧稿中的错误说法：本实现不是预先从后往前包装监听器，也没有通过继续函数替换参数的接口。可以讲“逐层进入、逐层返回”的可观察过程，但不能借别的中间件实现来补不存在的机制。

六、真实案例：谁来向用户追问缺失信息

回到测试排查。如果缺少复现条件，系统可能需要询问用户。负责发问的服务不该写死当前一定是网页界面。

问题事件的类型契约 说明请求和继续处理的形式。发问实现 把“没有回答者”的函数放在链尾。

作用域中某个处理者能回答，就返回结果；不负责，就交给后面。所有处理者都放行后，链尾抛出 NO_PROVIDER（没有可用回答者）。这不是默认成功，也不是模型已经得到用户同意。它只是一次提问没有找到承接方的明确失败。

第七讲的服务解决“找到提问入口”；本讲的接力链解决“提问由哪个参与者承接”。二者不是互相替代的两套名词，而是在同一任务的不同位置分工。

七、用一张契约表选路，再回源码核对

调用方式 等待什么 谁决定停止 本讲的直觉
emit（通知） 不等监听器的异步结果 同步异常仍可中断遍历 按门铃
parallel（并行等待） 所有监听器的最终结果 全部完成后汇总错误 等所有人交卷
bail（同步裁决） 不展开异步凭据 首个停止值 当场要答复
serial（逐个等待裁决） 当前监听器的最终值 首个最终停止值 等这人答完再问下一人
waterfall（包裹式接力） 由接力链返回值决定 当前处理者是否继续 门卫放行与回程处理

表里的顺序是比较顺序，不是一次任务依次经过五种模式。实际读源码时，先找事件类型，再找采用哪种分发方法，最后找监听者；缺任何一站都不能还原协作契约。

练习与答案

第八讲练习与答案

1. 通知是否表示办完

首个通知监听器同步抛错，第二个一定会执行吗？异步监听器返回后又是否表示异步工作完成？

展开答案

都不能保证。同步异常会打断这段遍历；正常返回也不等待异步结果。先区分有没有调用，再区分有没有完成。

2. 同样返回一个异步凭据

首个监听器返回 Promise.resolve(false)，同步裁决与逐个等待裁决有何不同？

展开答案

同步裁决看到凭据对象就停止；逐个等待裁决先得到最终的 false，按本项目规则继续问下一人。不要只凭方法名猜结果。

3. 继续函数能换参数吗

在本项目接力链里写 next(newInput)，是否能让下一层收到新参数？

展开答案

不能。本实现的继续函数不读取替换参数，下一层使用闭包中原有参数。真实示例应调用 next()。这不是所有中间件框架的通用规则，而是本源码的契约。

4. 所有人都放行

用户提问链中没有人接管，最后会怎样？

展开答案

到达末尾默认处理，抛出 NO_PROVIDER（没有可用回答者）。不能因此编造用户答复或授权。

5. 回到整条任务

为什么“能从上下文找到提问服务”仍不等于“这次问题一定有人回答”？

展开答案

服务查找解决入口可用性，接力分发解决当前请求由谁承接。两层分别有失败边界；需要继续核对作用域、监听者与是否调用继续函数。

遇到陌生词，先回到这个问题：一件事发生后，怎样让参与者按正确契约合作？ 以下是查阅页，正文会在需要时解释关键概念。英文只用于和源码对照；它不是额外的背诵任务。

英文与中文 直觉、实际职责与边界
Event（事件协作约定） 用事件名与参数组织处理，不自动等于可靠消息队列。
Listener（监听器） 登记参与一次事件处理的函数，不是后台线程的同义词。

next（继续后续处理） 本实现的继续函数不接收用于替换请求的参数。
fallback（末尾默认处理） 所有人都放行后才走到这里；默认处理可以抛错，未必成功。
