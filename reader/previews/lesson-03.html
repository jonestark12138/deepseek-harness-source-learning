第三讲逐步讲解 · 类型不只是标签，还是防错工装

源码快照：cd5ef8148158c3a752a658978873241fdf8e2bbc。

第二讲把类型当成任务包裹的标签。本讲向前一步：大型插件系统里，类型还要表达“哪个事件配哪些参数”“哪个插件给插件上下文增加什么”“哪些字符串虽然长得一样却不能混用”。

一、泛型：保存对应关系，不是把类型变模糊

延续同一任务：多个插件交换事件与标识时，编译器怎样帮我们防止接错线？下面每种语法都对应一种具体维护风险，不是要求一次背完语法大全。

Java 工程师可以先把 <T> 理解成“给类型留一个参数位”，但 TypeScript 泛型常与 keyof、索引访问一起使用。Cordis 的事件方法就是好例子：

emit<K extends keyof Events>(
  name: K,
  ...args: Parameters<Events[K]>
): void

证据在 vendor/cordis/src/events.ts#L34-L63。逐段翻译：

  • keyof Events 是 Events（事件契约集合） 所有键名组成的集合；
  • K extends ... 表示本次调用的 K 必须来自这个集合；
  • Events[K] 取出该事件名对应的监听函数类型；
  • Parameters<...> 再取出它的参数元组。

泛型在这里像可调尺寸的夹具：选定事件名后，参数槽位跟着调整。若只写成 name: string, ...args: any[]，语法更短，却丢失了事件名与参数之间的对应关系。

边界：这些generic（泛型）约束主要在编译期工作，不能替代运行时收到陌生事件名时的防御。

二、声明合并：给共同目录加一栏

上一节把事件名和参数绑在一起，可是插件可以随时增加能力，公共目录如何知道新字段？

Cordis 的 Context 是插件共享服务入口。工作空间包中出现：

declare module '@deepseek-ai/cordis' {
  interface Context {
    workspaceRegistry: WorkspaceRegistry
  }
}

见 packages/workspace/workspace/src/index.ts#L67-L71。

这叫module augmentation（模块声明扩展）：它告诉 TypeScript，“当你看 @deepseek-ai/cordis 的插件上下文时，还要把这一栏合进去。”多个插件可以各自扩展同一个接口，读者仍能得到统一的 ctx.xxx 提示。

但登记册不是设备本身。运行时还需要真实的 WorkspaceRegistry 服务被创建、提供并满足生命周期。只有 declare module，不会凭空出现 ctx.workspaceRegistry。

它和 Java 的感觉类似于多个模块共同丰富一份编译期契约，但机制不是修改某个已编译类，也不是 Spring 受容器管理的对象自动注册。

三、导入类型：只借说明书，不搬设备

目录有了新栏目，另一个文件怎样只引用栏目说明，而不误以为运行时设备已经装上？

同一个文件顶部既有普通导入，也有 import type（仅类型导入）：

import { Context, Service } from '@deepseek-ai/cordis'
import type { SessionHeader, SessionId } from '@deepseek-ai/dsh-session'
import type {} from '@deepseek-ai/dsh-session-persistence'

见 workspace/src/index.ts#L8-L16。

import type { X } 明确 X 只用于类型位置，发出的 JavaScript 不需要这条值导入。import type {} 则常用于引入声明扩展：它让 TypeScript 看见另一个模块提供的类型补充，却不制造运行时导入。

注意：这解释的是编译产物依赖，不等于“被提到的包在系统架构上没有运行时角色”。它可能由其他配置或插件路径在运行时加载。

四、品牌类型：给相同字符串发不同工牌

类型导入解决依赖表达，但两种不同编号都长成字符串时，还需要防止语义误接。

packages/util/brand/src/index.ts#L24-L27 定义：

declare const BRAND: unique symbol
export type Branded<B extends string> =
  string & { readonly [BRAND]: B }

随后工作空间包声明：

export type WorkspaceId = Branded<'WorkspaceId'>

于是 WorkspaceId 仍能像字符串一样记录、比较和序列化，但类型系统会把它与 SessionId 等其他品牌区分开。构造函数 WorkspaceId(id: string) 内部只是断言，源码注释明确说运行时仍是同一个字符串。

为什么有用？结构类型系统通常认为形状相同就兼容；跨代码包的多个定位编号都是字符串，最容易传错。品牌像不同用途工牌，弥补“外形相同却语义不同”的缺口。

边界：品牌不验证字符串格式，也阻止不了 as WorkspaceId 的强制断言。它是编译期防误接，不是密码学或运行时权限。

五、satisfies never（穷尽性检查表达式）：新状态来了，旧分支选择必须报警

编号防错只管参数。任务最终还有成功、取消和失败等分支，新增合法状态时怎样让旧处理代码报警？

stopReasonError() 处理 completed、cancelled、error 后，在默认分支写：

result.stopReason satisfies never

如果前三个分支已穷尽联合类型，默认分支中的值理论上不可能存在，类型应缩小成 never。未来有人新增 timed-out 却没补分支，编译器会在这里报错。

这像关门前点名：不是说意外永远不会发生，而是把“新增一种合法状态却忘记处理”的维护错误变成编译失败。源码仍保留防御性默认分支，因此面对异常运行时值还会生成错误描述。

六、.ts 相对导入：地址写法由整个构建约定决定

前面都在读模块内的约束。真正跳到另一个文件时，还会遇到相对路径后缀；它要回到工程配置解释。

仓库源码常写：

import { WorkspaceEntity } from './entity.ts'

根 tsconfig.base.json#L6-L18 同时设置：

  • module: esnext
  • moduleResolution: bundler
  • allowImportingTsExtensions: true
  • rewriteRelativeImportExtensions: true

因此在这个仓库里，源码可以明确写 .ts，编译输出会重写相对扩展名。它改善源码定位，也让导入与真实源文件对应。

不要把它复制成“所有 Node.js（JavaScript 运行环境） 标准模块机制都应该这样写”。能否写 .ts、运行器是否直接执行 TypeScript、输出要变成 .js 还是由打包器接管，都取决于项目配置和工具链。

  2. packages/workspace/workspace/src/index.ts：找 import type、declare module 和 WorkspaceId()。
  3. packages/util/brand/src/index.ts：看品牌原语为什么没有运行时代码。

八、一句话总结

泛型守住“名称与参数”的对应关系；声明合并让插件扩展共同契约；品牌类型阻止同形定位编号混用；satisfies never 守住状态分支的完整性；标准模块机制导入写法则由仓库的编译约定保证。它们都是防错工装，不是运行时能力本身。

练习与答案

第三讲练习与答案

练习 1：泛型保住了什么

为什么 emit<K extends keyof Events>(name: K, ...args: Parameters<Events[K]>) 比 emit(name: string, ...args: any[]) 更有用？

展开答案

前者把事件名限制在 Events（事件契约集合） 的键内，并根据具体事件名推出对应参数；后者允许任何名字和任何参数，丢掉了关系。两者仍都需要真实的运行时分发实现。

练习 2：只有 declare module（模块声明扩展语法） 会怎样

假设插件只写 declare module 增加 ctx.demo，却没有任何服务提供者或初始化代码。运行时会自动出现 demo（教学示例行） 吗？

展开答案

不会。声明扩展只改变编译器看到的类型形状。运行时属性要由真正的服务注册或对象赋值产生；否则访问可能得到 undefined（未定义值）或触发框架错误。

练习 3：品牌能防什么、不能防什么

展开答案

能在正常类型检查下防止 WorkspaceId（工作空间标识） 与其他字符串品牌混用；不能校验 UUID（通用唯一标识） 格式、提供运行时权限或阻止开发者强制类型断言。序列化后仍是普通字符串，边界输入需要重新验证和建立品牌。

练习 4：新增状态

若 WorkflowStopReason 新增 timed-out，但分支选择没有分支，会发生什么？

展开答案

在开启类型检查时，默认分支中 result.stopReason satisfies never 将不再成立，编译失败，提醒补上分支。若异常值绕过类型系统进入运行时，防御性默认分支仍会返回异常描述。

练习 5：导入类型的误区

判断：“使用 import type {} 就证明这个代码包在整个系统运行时完全没用。”

展开答案

错误。它只说明当前导入不生成值依赖。该代码包可能通过配置、别的值导入或插件加载器参与运行。

第3讲术语与比喻词典

遇到陌生词，先回到这个问题：名字都像字符串，怎样避免把错误参数接到错误能力？ 以下是查阅页，正文会在需要时解释关键概念。英文只用于和源码对照；它不是额外的背诵任务。

英文与中文 直觉、实际职责与边界
generic（泛型） 像可调夹具，在多种类型中保留输入输出或名字参数的对应关系。
module augmentation（模块声明扩展） 往共同类型登记册加一栏，不会真的把服务设备安装进去。
import type（仅类型导入） 只借类型说明，不通过这一条导入搬入运行时值。
Branded（品牌化标识类型） 给同是字符串的编号加编译期身份，像不同用途工牌；不是权限校验。
never（不可能值类型） 在穷尽分支后表示不应再有合法剩余值；帮助发现漏处理的新状态。
ESM（标准模块机制） 用导入导出组织代码，实际路径写法还受项目编译与运行配置约束。
