# 第 01 次分享稿：Model 会“想”，Harness 才让它持续“做”

> 建议时长：15 分钟
>
> 目标：让听众带走一个空间隐喻、一张正式架构图和一条源码路线。
> 源码基准：[`cd5ef8148158c3a752a658978873241fdf8e2bbc`](https://github.com/deepseek-ai/deepseek-harness/tree/cd5ef8148158c3a752a658978873241fdf8e2bbc)

## 0:00–1:30｜开场：一个被关在玻璃房里的天才

大家先想象一个非常聪明的人。他能理解复杂需求，也能给出漂亮方案，但被关在玻璃房里：没有门、没有工具柜、没有工作日志，也不知道哪些动作被允许。

如果我们只给他一句“检查仓库并修复问题”，他可以告诉你“应该先找入口、再改代码、最后运行测试”，但真实文件不会因此被读取，真实命令也不会因此执行。

这就是今天的驱动问题：

> 一个只会推理和生成的 Model，怎样被组织成能连接真实环境、保存过程并持续工作的系统？

## 1:30–4:00｜第一张图：Model 是大脑，不是整台机器

![只有 Model 与 Model 加 Harness 的职责对比](../assets/lesson-01/fig-01-model-vs-harness.svg)

左边只有 Model。它擅长理解、推理和生成，但没有自己的文件系统、Session 或 Sandbox。

右边把 Model 放进 Harness。Tool、Skill、Filesystem 提供能力，Session 提供连续性，Sandbox 提供执行边界。

可以先用一句教学近似：

> Agentic System ≈ Model + Harness。

马上补充边界：这不是 DeepSeek Harness 源码中 `Agent` 接口的定义。源码把 Agent handle/registry 和默认 Agent Loop driver 放在不同 package。

**停顿提问：**如果换一个更强 Model，右边的 Filesystem 权限会自动出现吗？答案不会。更会思考，不等于更有权限。

## 4:00–7:00｜第二张图：进入模块化智能工作室

![模块化智能工作室](../assets/lesson-01/fig-02-modular-workshop.svg)

为了记住这些角色，我们进入一间模块化智能工作室。

- Model 是推理工作台。
- Harness 是整套工作安排，不是一个同级小框。
- Cordis 是模块轨道、依赖激活与生命周期机制。
- Plugin 是挂上轨道的模块。
- Tool 是动作端口，Skill 是操作手册。
- Session 是不断追加的工作日志。
- Sandbox 是受策略约束的执行区。

这里最容易混淆 Tool 与 Skill。Skill 可以告诉模型“怎样进行源码审查”，但真正读取文件、运行命令，仍要靠 Tool 和环境能力。

再补比喻边界：Cordis 不是操作系统，Skill 也不是可执行工具。接下来我们把工作室拿掉，回到真实架构。

## 7:00–9:30｜第三张图：核心为什么也是插件

![从硬编码主函数到 Cordis 插件树](../assets/lesson-01/fig-03-everything-is-plugin.svg)

左边像一块焊死的主板：LLM、Tools、Session、Loop 全塞进 `main()`。换一个模型，可能碰到状态代码；测试一个工具，可能要启动整台机器。

右边是一条 Cordis 模块轨道。Profile 决定这次启动挂上哪些模块，模块通过稳定 capability seam 提供和消费能力。

上游架构文档明确说，model adapter、tool registry、session log、agent loop 自己也都是插件。所以“Everything is a Plugin”不是“支持第三方扩展”这么简单，而是核心本身也遵循同一组合模型。

但可替换不等于随便替换。契约、依赖、生命周期和行为兼容仍然需要验证。

## 9:30–12:00｜正式架构：把比喻映射回源码

![DeepSeek Harness 第一层正式架构](../assets/lesson-01/fig-04-first-layer-architecture.svg)

现在只看六个主元素：

1. CLI 和 Profile 负责选择与组合。
2. Cordis Context 承载 plugin tree。
3. Base bundle 把 LLM、Agent、Session、Tools、System Prompt、Agent Loop 等装入组合。
4. Capability seam 用 Definition、Provider、Consumer 形成稳定接缝。
5. Session 记录 append-only events，并派生模型历史。
6. Environment/UI 提供 Terminal、Filesystem、Sandbox 与用户输入。

注意图中没有把 Cordis 画成 OS，也没有把 Model 画成 Filesystem 的拥有者。

## 12:00–14:00｜源码路线：到 `boot()` 就下车

![源码阅读地铁线](../assets/lesson-01/fig-05-source-reading-route.svg)

第一次打开大仓库，不要从最深的算法开始。按五站走：

1. `docs/architecture.md`：先拿全景地图。
2. `apps/cli/src/bin.ts`：profile 模式委托给 `runProfile()`。
3. `apps/cli/src/profile-boot.ts`：`composeProfile()` 与 `allPatches()` 组合 layers。
4. `packages/bundle/base/cordis.patch.yml`：确认核心 entry 也通过配置进入组合。
5. 回到 `runProfile()`：看到最终 `boot()`。

到这里就下车。第一讲的任务是理解“怎样组成”，不是一次读懂 Loader、Fiber、Agent Loop 和 Session 内部。

顺带提醒一个源码阅读纪律：YAML 行号可以证明 entry 在配置中出现，不能单独证明插件真实激活顺序。

## 14:00–15:00｜收束与提问

今天只带走三句话：

1. Model 负责想，Harness 负责让思考接触能力、状态和规则。
2. DeepSeek Harness 的核心也是插件，Cordis 把它们组织成可组合的 plugin tree。
3. 第一次源码阅读沿 `architecture -> bin.ts -> profile-boot.ts -> base bundle -> boot()`，在边界停下。

最后请大家回答：

> 如果明天要替换一个 LLM Provider，哪些部分理论上可以保持稳定？哪些兼容性仍必须验证？

这个问题能答清，说明你已经从“记住几个方框”走到了“理解系统为什么这样组织”。
