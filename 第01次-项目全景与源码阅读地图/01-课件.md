# 第 01 次课件：Model 会“想”，Harness 才让它持续“做”

> 源码基准：[`cd5ef8148158c3a752a658978873241fdf8e2bbc`](https://github.com/deepseek-ai/deepseek-harness/tree/cd5ef8148158c3a752a658978873241fdf8e2bbc)
> 驱动问题：一个 Model 怎样被组织成能连接真实环境、保存过程并持续工作的 Agentic System？

---

## 01｜先别背定义：把 Model 放进真实任务

假设你对 Model 说：

> “阅读仓库，定位启动链，修改教材，运行检查，再根据失败结果继续修正。”

Model 可以理解目标、推理和生成文本，但真实任务还需要有人回答这些问题：

- 仓库内容从哪里读？
- 哪些动作允许执行？
- 上一步结果记在哪里？
- 失败后怎样继续下一步？
- 换一个模型或工具时，系统是否要推倒重来？

![只有 Model 与 Model 加 Harness 的职责对比](../assets/lesson-01/fig-01-model-vs-harness.svg)

> 图 01-01：Model 是推理焦点；Harness 是组织能力、状态与约束的系统边界。

### 现在记住

> **教学近似：Agentic System ≈ Model + Harness。**

但源码中的 `Agent` 更具体：`dsh-agent` 拥有 Agent handle、live registry 与事件词汇，默认创建和驱动逻辑在 `dsh-agent-loop`。不要把开场公式当成 TypeScript 类型定义。

---

## 02｜进入一间“模块化智能工作室”

第一次接触 Harness 时，最难的不是名词多，而是名词没有空间位置。先借一间工作室建立直觉。

![模块化智能工作室：Model、Cordis、Plugin、Tool、Skill、Session 与 Sandbox](../assets/lesson-01/fig-02-modular-workshop.svg)

> 图 01-02：Model 在工作室里负责推理；Harness 让模块、能力、记录和受控执行共同工作。

| 工作室里的东西 | 映射到真实概念 | 不要误解成 |
|---|---|---|
| 推理工作台 | Model / LLM 调用能力 | 整个 Agentic System |
| 工作室边界 | Harness | 一个与 Tool 平级的组件 |
| 模块轨道 | Cordis Context、依赖与生命周期 | 操作系统或 Sandbox |
| 可挂模块 | Plugin | 仅第三方 IDE 插件 |
| 动作端口 | Tool | 一定获准执行的命令 |
| 操作手册 | Skill | 可执行能力本身 |
| 工作日志 | Session | 普通聊天消息数组 |
| 受控执行区 | Sandbox | 任何时候都等于容器或 VM |

### 比喻在哪里失效

这不是一张正式架构图。Cordis 不是真实轨道，Plugin 也不是物理设备。比喻只负责帮你记住职责位置；接下来必须把它换回 Context、service key、配置行和 package。

## 03｜如果所有能力都焊死在 `main()` 里

把 LLM、Tools、Session、Agent Loop 都写进一个主函数，短期看很直接，长期会出现三个问题：

1. 替换模型会碰到状态和工具代码。
2. 测试某个能力需要启动整台机器。
3. 不同部署场景难以裁剪或叠加能力。

![从硬编码主函数到 Cordis 插件树](../assets/lesson-01/fig-03-everything-is-plugin.svg)

> 图 01-03：插件化不是“文件更多”，而是变化沿稳定接缝被隔离，并随生命周期装上或卸下。

DeepSeek Harness 的架构文档明确说明：model adapter、tool registry、session log、agent loop 自己也都是 Cordis 插件。运行中的 `dsh` 是启动时由 profile 与 bundle 组成的 plugin tree。

### 和 Spring 的第一座桥

| 相似点 | 不能画等号的地方 |
|---|---|
| 都通过容器、依赖与生命周期把实现组织起来 | Cordis 的 Context、Fiber、Service 和 effect 语义不是 Spring API |
| 消费方依赖稳定能力键，而不是到处 `new` 实现 | Service Definition 不只是 TypeScript interface |
| 不同配置可以组合不同实现 | patch 应用顺序不等于插件真实激活顺序 |

## 04｜把比喻拿掉：第一层正式架构

![DeepSeek Harness 第一层正式架构](../assets/lesson-01/fig-04-first-layer-architecture.svg)

> 图 01-04：CLI/Profile 组合 Cordis 插件树；插件通过 capability seams 接入环境能力，并用 Session 事件日志保持连续性。

### 六个主元素

- **CLI + Profile**：解析调用，选择 profile，叠加 patch。
- **Cordis Context / plugin tree**：承载插件生命周期、services、events 与 effects。
- **Base bundle plugins**：LLM、Agent、Session、Tools、System Prompt、Agent Loop 等基础插件。
- **Capability seams**：Definition / Provider / Consumer 形成稳定接缝。
- **Session log**：追加事件，再派生模型可见历史。
- **Environment + UI**：Terminal、Filesystem、Sandbox、用户输入等外部表面。

### 现在不要深入

这张图故意没有展开 Fiber、事件 dispatch、Agent Loop 状态机、Session projection、工具审批和 Sandbox 后端。第一讲先拿到“组件放在哪里、怎样组合”的地图。

## 07｜一页收束

### 三句话

1. Model 擅长理解、推理和生成；Harness 负责把它放进一个可持续运行的系统。
2. DeepSeek Harness 的核心也是插件，Cordis 通过 Context、依赖和生命周期把它们组合起来。
3. 第一次源码阅读沿 `architecture -> bin.ts -> profile-boot.ts -> base bundle -> boot()`，到边界就停。

### 三组不要混淆

| A | B | 区别 |
|---|---|---|
| Tool | Skill | 动作端口 vs 可复用指令 |
| Agent | Agent Loop | 运行对象/registry/event vocabulary vs 默认创建与驱动插件 |
| Session | persistence | 事件日志与派生历史 vs 独立持久化实现 |

### 下课前 30 秒自测

- 为什么换更强模型仍不能自动获得文件系统和执行权限？
- 为什么 `agent-loop` 出现在 base bundle 能支持“核心也是插件”？
- 为什么看到 YAML 行号不能推断真实插件激活顺序？
- 为什么第一讲不应该从 Agent Loop 内部实现开始？
