## 5. 参考答案

<details>
<summary>展开基础理解题答案（题 1–10）</summary>

### 题 1 答案

Model 根据输入消息产生内容或工具调用意图。Harness 负责准备上下文、暴露和执行工具、维护状态、实施权限策略、连接真实环境并驱动后续步骤。模型能力再强，也不会自动获得文件、进程、授权和可恢复的持续状态。

### 题 2 答案

Agent 是 Model 与 Harness 共同形成的运行实例；agent loop 是 Harness 中驱动 turn 和 step 的一个组件。题目中的说法不正确，因为 DeepSeek Harness 还包含 Session、提示词组装、工具管线、LLM adapter、执行能力、持久化、权限和产品协议，而且 loop 自身也是可替换插件。

### 题 3 答案

不是。内置的 Session、LLM、Agent、Tools、System Prompt 和 Agent Loop 等也由 Cordis 插件组合。答出其中任意三个即可。

### 题 4 答案

Context 为插件提供受管理的服务发现、事件通信和生命周期资源。它不只是全局单例容器，因为 Cordis 还依据 service 依赖激活插件，并在插件释放时撤销它拥有的 effect。

### 题 5 答案

插件可能已经注册服务、事件监听器、计时器或其他资源。只停止新调用不会移除这些既有注册，它们仍可能响应事件、占用资源或影响新配置；disposer 负责撤销这些副作用。

### 题 6 答案

理想情况下更换文件能力的 Provider 或相关配置，Consumer 继续依赖稳定的 Service Definition。若文件、Shell、子进程、终端和 LSP 必须处在同一执行世界，还要一起检查这些 provider 的组合，但不应要求每个消费方改为依赖新具体类。

### 题 7 答案

base bundle 的源码注释说明行顺序主要用于读者分组，激活由 service availability 驱动。YAML 顺序可以影响 patch 文本的组织，但不能直接等同于 Cordis 的运行时依赖激活顺序。

### 题 8 答案

一个机制经常跨 package、配置、事件和测试。如果以目录为单位，很容易无目标地遍历文件；以问题为单位可以只追与结论相关的 manifest、公开入口、实现、配置和测试。

### 题 9 答案

源码主要解释实现和类型关系；配置解释模块怎样进入真实组合；测试解释行为、失败和可观察结果。单类证据可能遗漏装配或误把测试环境当成产品环境，两类以上证据更容易暴露误读。

### 题 10 答案

`boot()` 内部涉及 Cordis Context、Loader、Fiber、effect 与依赖激活；agent loop 又依赖 Session、System Prompt、LLM 和 Tools。先建立这些先修概念，才能避免把框架行为误读成局部函数行为。

### 题 22 参考答案

DeepSeek Harness 把模型接入上下文、工具、状态和真实环境，使 Agent 能持续完成多步骤任务。它基于 Cordis，把 Session、模型、工具和 Agent Loop 等核心能力都作为可组合、可卸载的插件。第一次阅读源码应从 `apps/cli/src/bin.ts` 开始，再到 `profile-boot.ts` 和 base bundle，而不是顺序遍历整个 monorepo。

### 题 23 参考关系

用户目标先进入 Harness；Harness 组装消息并调用 Model；Model 返回内容或工具调用意图；Harness 的 Agent Loop 把工具调用交给 Tools；Tools 经过宿主策略后操作文件或进程环境；结果和模型输出写入 Session，再进入下一 step 或返回用户。

### 题 24 参考改写

`bin.ts` 解析参数并把 profile 启动责任交给 `runProfile()`，并不直接创建所有核心服务。base bundle 声明插入 `agent-loop` 等插件行，但 YAML 中的位置不能证明它最后激活。`id: tools` 证明工具服务被纳入组合；具体工具是否获准并安全执行，还取决于参数验证、执行 pipeline、策略、审批和 provider 行为。
