这讲只解决一个问题

一个只会理解、推理和生成的 Model，怎样被组织成能够连接真实环境、保存过程并持续完成多步骤工作的 Agentic System？

Model 负责“想”；Harness 负责把能力、状态、约束与下一步组织起来。

这里的“Agentic System ≈ Model + Harness”是教学近似，不是 DeepSeek Harness 源码中 Agent 接口的定义。

视觉课件

第 01 次课件：Model 会“想”，Harness 才让它持续“做”

源码基准：cd5ef8148158c3a752a658978873241fdf8e2bbc 驱动问题：一个 Model 怎样被组织成能连接真实环境、保存过程并持续工作的 Agentic System？

01｜先别背定义：把 Model 放进真实任务

假设你对 Model 说：

“阅读仓库，定位启动链，修改教材，运行检查，再根据失败结果继续修正。”

Model 可以理解目标、推理和生成文本，但真实任务还需要有人回答这些问题：

  • 仓库内容从哪里读？
  • 哪些动作允许执行？
  • 上一步结果记在哪里？
  • 失败后怎样继续下一步？
  • 换一个模型或工具时，系统是否要推倒重来？

图 01-01：Model 是推理焦点；Harness 是组织能力、状态与约束的系统边界。

现在记住

教学近似：Agentic System ≈ Model + Harness。

但源码中的 Agent 更具体：dsh-agent 拥有 Agent handle、live registry 与事件词汇，默认创建和驱动逻辑在 dsh-agent-loop。不要把开场公式当成 TypeScript 类型定义。

02｜进入一间“模块化智能工作室”

第一次接触 Harness 时，最难的不是名词多，而是名词没有空间位置。先借一间工作室建立直觉。

图 01-02：Model 在工作室里负责推理；Harness 让模块、能力、记录和受控执行共同工作。

工作室里的东西 映射到真实概念 不要误解成
推理工作台 Model / LLM 调用能力 整个 Agentic System
工作室边界 Harness 一个与 Tool 平级的组件
模块轨道 Cordis Context、依赖与生命周期 操作系统或 Sandbox
可挂模块 Plugin 仅第三方 IDE 插件
动作端口 Tool 一定获准执行的命令
操作手册 Skill 可执行能力本身
工作日志 Session 普通聊天消息数组
受控执行区 Sandbox 任何时候都等于容器或 VM

比喻在哪里失效

这不是一张正式架构图。Cordis 不是真实轨道，Plugin 也不是物理设备。比喻只负责帮你记住职责位置；接下来必须把它换回 Context、service key、配置行和 package。

03｜如果所有能力都焊死在 main() 里

把 LLM、Tools、Session、Agent Loop 都写进一个主函数，短期看很直接，长期会出现三个问题：

  1. 替换模型会碰到状态和工具代码。
  2. 测试某个能力需要启动整台机器。
  3. 不同部署场景难以裁剪或叠加能力。

图 01-03：插件化不是“文件更多”，而是变化沿稳定接缝被隔离，并随生命周期装上或卸下。

DeepSeek Harness 的架构文档明确说明：model adapter、tool registry、session log、agent loop 自己也都是 Cordis 插件。运行中的 dsh 是启动时由 profile 与 bundle 组成的 plugin tree。

和 Spring 的第一座桥

相似点 不能画等号的地方
都通过容器、依赖与生命周期把实现组织起来 Cordis 的 Context、Fiber、Service 和 effect 语义不是 Spring API
消费方依赖稳定能力键，而不是到处 new 实现 Service Definition 不只是 TypeScript interface
不同配置可以组合不同实现 patch 应用顺序不等于插件真实激活顺序

04｜把比喻拿掉：第一层正式架构

图 01-04：CLI/Profile 组合 Cordis 插件树；插件通过 capability seams 接入环境能力，并用 Session 事件日志保持连续性。

六个主元素

  • CLI + Profile：解析调用，选择 profile，叠加 patch。
  • Cordis Context / plugin tree：承载插件生命周期、services、events 与 effects。
  • Base bundle plugins：LLM、Agent、Session、Tools、System Prompt、Agent Loop 等基础插件。
  • Capability seams：Definition / Provider / Consumer 形成稳定接缝。
  • Session log：追加事件，再派生模型可见历史。
  • Environment + UI：Terminal、Filesystem、Sandbox、用户输入等外部表面。

现在不要深入

这张图故意没有展开 Fiber、事件 dispatch、Agent Loop 状态机、Session projection、工具审批和 Sandbox 后端。第一讲先拿到“组件放在哪里、怎样组合”的地图。

07｜一页收束

三句话

  1. Model 擅长理解、推理和生成；Harness 负责把它放进一个可持续运行的系统。

逐步讲解

第 01 次逐步讲解：从一颗聪明的大脑，到一套能持续工作的系统

源码基准：cd5ef8148158c3a752a658978873241fdf8e2bbc 阅读约定：文中明确区分 源码事实、教学近似 与 比喻。

1. 先体验缺口：聪明不等于能完成任务

想象一位非常聪明、但被关在玻璃房里的人。他能理解你的问题，也能给出周密方案，却没有门、工具柜、工作日志和安全规则。

你让他“检查仓库并修复问题”，他可以推理“应该搜索入口、修改文件、运行测试”，但仅靠推理不能让这些动作在真实机器上发生。

这正是 Model 与 Harness 的第一层差异：

图 01-01：Model 提供推理与生成；Harness 把模型接入能力、状态与执行边界。

1.1 源码事实

DeepSeek Harness 把职责分散在不同 package：

  • dsh-llm 提供 provider-neutral model-call service。
  • dsh-tools 拥有模型可见工具注册与 guarded execution pipeline。
  • dsh-session 拥有 append-only 事件日志与派生历史。
  • dsh-sandbox 负责受策略约束的进程执行。

因此，“Model 不直接拥有 Filesystem、Session 或 Sandbox”不是审美偏好，而是 package 职责分离带来的事实。

1.2 教学近似

Agentic System ≈ Model + Harness

这句话只帮助建立开场直觉。源码中的 Agent 不是这个等式：dsh-agent 拥有 Agent handle、live registry 与 agent/* 事件；默认创建和驱动由 dsh-agent-loop 提供。

如果把近似当成源码定义，后面阅读 Agent 接口时一定会困惑。

2. 先建立空间，再学习名词

抽象名词最难记，是因为它们在脑中没有位置。现在进入一间“模块化智能工作室”。

图 01-02：比喻只负责建立职责位置；真实机制仍要回到 Context、Plugin、Service 和配置。

2.1 映射

Model：推理工作台

它读到模型可见的 messages 与 tool schemas，产生文本或 tool call。它不是工作室本身。

Harness：整套工作安排

Harness 不是单个 class 的名字，而是把上下文、能力、策略、状态和继续执行组织起来的系统性角色。

Cordis：模块轨道与能力登记

Cordis 的 primer 把核心概括为 Plugin、Context、inject、typed events 与 reversible effects。Plugin 向共享 Context 贡献能力；依赖未满足时，可通过 inject 等待 service 出现。

和 Spring 的相似点是：两者都帮助组织依赖、生命周期和扩展。不同点是：Cordis 的 Context/Fiber/Service/effect 有自己的语义，不能直接翻译成 ApplicationContext、Bean 与 @EventListener。

Tool 与 Skill：设备和说明书

  • Tool 是模型可见的动作定义及受保护的执行路径。
  • Skill 是 provider 提供、registry 合并、consumer 公开并通过 loader tool 加载的可复用指令。

所以 Skill 可以告诉模型“怎样系统化审查 Spring Boot 项目”，但真正读取文件、运行命令仍依赖 Tool 与环境能力。

Session：工作日志

Session 的重点是 append-only event log。模型历史从日志派生，持久化由独立实现提供。把它理解成聊天消息数组，会看不到 tool result、状态变化和恢复语义。

Sandbox：受控执行区

Sandbox 对 subprocess 施加策略边界。它不天然等于 Docker、microVM 或远程执行器，也不等于“工作目录”这个普通路径概念。

2.2 比喻边界

比喻会偷偷引入不存在的事实。例如“轨道”容易让人以为插件按物理顺序启动，“设备”容易让人以为 Tool 一定执行成功。正式结论只能来自源码、配置和维护文档。

3. 为什么核心也要插件化

如果把 LLM、Tools、Session、Agent Loop 全部写进主函数，系统看起来更短，却把变化源焊在一起。

图 01-03：插件化的价值是隔离变化和组合生命周期，不是追求更多文件。

3.1 上游架构给出的关键事实

docs/architecture.md 明确说明：model adapter、tool registry、session log、agent loop 本身都是插件；运行中的 dsh 是在 boot 时组成的 plugin tree。

这意味着“Plugin”不只指用户后来安装的扩展。核心能力本身也遵循同一组合模型。

3.2 稳定接缝是什么

完整 capability seam 包括：

角色 直觉 本讲只记什么
Definition 定义稳定服务键和词汇 消费方认 ctx.<key>
Provider 提供具体实现 可以替换，但要满足契约
Consumer 注入并使用能力 不直接依赖某个实现文件

Service Definition 不是“一个 TypeScript interface”这么简单。它还拥有稳定 key 与词汇。完整实现留到后续课程。

3.3 可替换不等于随便替换

插件化只提供结构上的替换点。真实替换仍受契约、依赖、配置、生命周期和行为兼容约束。不要从“都是插件”推出“任意模块可以无成本互换”。

4. 从工作室回到正式架构

图 01-04：CLI/Profile 决定如何组成 Cordis plugin tree；运行时通过稳定能力接缝与日志连接外部世界。

现在逐一把比喻还原：

  1. 工作室方案 → Profile、bundle 与 patch stack。
  2. 模块轨道 → Cordis Context 和 plugin tree。
  3. 可插模块 → base bundle 中的 LLM、Agent、Session、Tools、System Prompt、Agent Loop 等 entry。
  4. 能力插座 → Definition / Provider / Consumer 与 ctx.<key>。
  5. 工作日志 → append-only Session events 与 derived model history。
  6. 外部设备 → Terminal、Filesystem、Sandbox、UI 等 provider/consumer 组合。

注意，图中箭头有明确语义：boot 表示配置组合进入 Context，provide/inject 表示服务接缝，append/derive 表示日志关系，调用 表示通过能力接入外部环境。箭头不是装饰。

5. 进入源码：第一站是入口，不是核心算法

图 01-05：第一次阅读的任务是找到装配链，而不是证明自己能钻进最深的实现。

5.1 为什么现在看 bin.ts

我们要确认 CLI 把 profile 模式委托给谁。

const invocation = parseDshArgs(process.argv.slice(2), readVersion())

switch (invocation.mode) {
  case 'profile': {
    const { runProfile } = await import('./profile-boot.ts')
    await runProfile({
      environment: loadLayeredEnv('dsh'),
      profile: invocation.profile,
      patchFiles: invocation.patches,
      args: invocation.args,
    })
    break
  }
}

来源：apps/cli/src/bin.ts#L24-L35

看三个地方：

  1. parseDshArgs() 先把命令行变成结构化 invocation。
  2. profile 模式动态导入 profile-boot.ts。
  3. 环境、profile、patch 与 inner args 一起交给 runProfile()。

入口没有构建 Model、Tools 或 Session。它只负责解析和委托。

5.2 为什么现在看 allPatches() 与 composeProfile()

我们要确认 profile 如何变成实际 patch stack。

function allPatches(composed: ComposedProfile): PatchOptions[] {
  return [
    ...composed.bundlePatches,
    ...composed.profile.patches,
    ...composed.homePatches,
    ...composed.overlays,
  ]
}

async function composeProfile(name: string, patchFiles: readonly string[]) {
  const profile = prepareProfile(name)
  const homePatches = loadOptionalPatches(NAME, homePatchPath()) ?? []
  const overlays = patchFiles.flatMap(file => loadOverlayPatches(NAME, resolve(file)))
  const bundlePatches = profile.layers.flatMap(layer => layer.patches)
  // ...
  return { profile, bundlePatches, homePatches, overlays: composedOverlays }
}

来源：apps/cli/src/profile-boot.ts#L136-L172

看四个层次：bundle、profile、自机 home layer、命令行 overlays。它们说明“这次运行怎样组合配置”，但还不能证明每个插件何时激活。

5.4 为什么在 boot() 停下

export async function runProfile(options: RunProfileOptions) {
  const composed = await composeProfile(options.profile, options.patchFiles)
  // ... shutdown and live-reload setup ...
  const ctx = await boot(
    NAME,
    rootConfig,
    structuredClone(allPatches(composed)),
    hostCtx => {
      hostCtx.provide(DSH_LAUNCH_ENVIRONMENT_KEY, options.environment)
      provideCmdline(hostCtx, { args: options.args, /* ... */ })
    },
  )
  // ...
}

现在闭眼复述：

  1. Model 是工作室里的推理核心。
  2. Harness 是让它能接触能力、状态和规则的完整安排。

第 01 次练习与答案

源码基准：cd5ef8148158c3a752a658978873241fdf8e2bbc 使用方式：先完成题目并写下理由，再展开答案。目标是检验心智模型，不是背名词。

A. 30 秒解释题

1. 为什么换一个更强的 Model，仍不能自动获得文件读取、命令执行和跨轮状态？

参考答案

因为这些职责由 Harness 中的不同能力拥有，而不是模型权重的一部分。模型调用接收 messages 与 tool schemas，产生文本或 tool call；Filesystem、Tools、Session、Sandbox 分别由对应 package/provider 提供。

更强的 Model 可能更会选择动作，却不会凭空创造操作系统权限、工具实现、状态日志和安全策略。

证据：dsh-llm、dsh-tools、dsh-session、sandbox。

2. “Agentic System ≈ Model + Harness”为什么只能作教学近似？

参考答案

它能说明完整系统需要“推理中心 + 运行支撑”，但源码中的 Agent 是更具体的运行对象。dsh-agent 拥有 Agent handle、live registry 和 agent/* 事件，默认创建和驱动逻辑由 dsh-agent-loop 提供。

因此不能把该公式写成源码 Agent 接口定义。

证据：packages/core/agent/README.md。

4. Cordis Context 与 Spring ApplicationContext 有什么相似和不同？

参考答案

相似：都帮助组织依赖、生命周期、服务发现和扩展，消费方不必直接构造具体实现。

不同：Cordis 有自己的 Plugin、Fiber、Service、typed event 与 reversible effect 语义；Service Definition 还拥有稳定 ctx.<key> 和词汇，不能直接等同于 Java interface 或 Spring Bean 定义。

C. 机制与预测题

5. 把 LLM、Tools、Session、Agent Loop 都做成插件，主要解决什么问题？

参考答案

主要解决变化隔离和组合问题：不同 profile 可以装配不同插件，provider 可以在稳定 capability seam 后替换，插件还能参与统一依赖与生命周期。

它不保证任意插件可以无成本互换；契约、依赖、配置和行为兼容仍然存在。

6. 如果一个 Consumer 只依赖稳定的 ctx.<key>，替换 Provider 后理论上什么可以不变？什么仍需验证？

参考答案

理论上 Consumer 的调用位置与业务流程可以不变，因为它依赖稳定服务键和契约，而不是某个实现文件。

仍需验证：新 Provider 是否完整实现契约、是否满足依赖、生命周期是否兼容、错误和性能语义是否变化，以及配置是否正确加载。

7. 为什么 Session 不应该直接等同于数据库？

参考答案

Session 的核心职责是 append-only event log 和 derived model history；持久化是独立关注点。数据库可以是某种 persistence 实现，但不是 Session 概念本身。

证据：packages/core/session/README.md。

E. 结论校准题

10. 改写过强结论：“Model 直接调用文件系统。”

参考答案

更准确：Harness 向 Model 提供模型可见的工具 schema；Model 可以返回 tool call。具体工具由 Harness 的 registry 与 guarded pipeline 调用相应 capability/provider，Filesystem 或 Sandbox 在模型外部执行并返回结果。

11. 改写过强结论：“YAML 中后写的插件一定最后启动。”

参考答案

更准确：YAML 行序和 patch stack 能提供配置组合证据，但插件实际激活还受 Cordis 依赖解析、inject、生命周期与运行条件影响。未检查 Loader/Fiber 或运行证据前，不能把文件顺序当成激活顺序。

12. 改写过强结论：“Sandbox 就是一个 Docker 容器。”

参考答案

更准确：本仓库的 Sandbox group 为 subprocess 执行提供策略约束和平台后端；它可能被更强隔离实现替换，但 generic sandbox icon 不能推断容器、microVM 或远程执行。

0:00–1:30｜开场：一个被关在玻璃房里的天才

大家先想象一个非常聪明的人。他能理解复杂需求，也能给出漂亮方案，但被关在玻璃房里：没有门、没有工具柜、没有工作日志，也不知道哪些动作被允许。

如果我们只给他一句“检查仓库并修复问题”，他可以告诉你“应该先找入口、再改代码、最后运行测试”，但真实文件不会因此被读取，真实命令也不会因此执行。

这就是今天的驱动问题：

一个只会推理和生成的 Model，怎样被组织成能连接真实环境、保存过程并持续工作的系统？

1:30–4:00｜第一张图：Model 是大脑，不是整台机器

左边只有 Model。它擅长理解、推理和生成，但没有自己的文件系统、Session 或 Sandbox。

右边把 Model 放进 Harness。Tool、Skill、Filesystem 提供能力，Session 提供连续性，Sandbox 提供执行边界。

可以先用一句教学近似：

Agentic System ≈ Model + Harness。

马上补充边界：这不是 DeepSeek Harness 源码中 Agent 接口的定义。源码把 Agent handle/registry 和默认 Agent Loop driver 放在不同 package。

**停顿提问：**如果换一个更强 Model，右边的 Filesystem 权限会自动出现吗？答案不会。更会思考，不等于更有权限。

4:00–7:00｜第二张图：进入模块化智能工作室

为了记住这些角色，我们进入一间模块化智能工作室。

  • Model 是推理工作台。
  • Harness 是整套工作安排，不是一个同级小框。
  • Cordis 是模块轨道、依赖激活与生命周期机制。
  • Plugin 是挂上轨道的模块。
  • Tool 是动作端口，Skill 是操作手册。
  • Session 是不断追加的工作日志。
  • Sandbox 是受策略约束的执行区。

这里最容易混淆 Tool 与 Skill。Skill 可以告诉模型“怎样进行源码审查”，但真正读取文件、运行命令，仍要靠 Tool 和环境能力。

再补比喻边界：Cordis 不是操作系统，Skill 也不是可执行工具。接下来我们把工作室拿掉，回到真实架构。

7:00–9:30｜第三张图：核心为什么也是插件

左边像一块焊死的主板：LLM、Tools、Session、Loop 全塞进 main()。换一个模型，可能碰到状态代码；测试一个工具，可能要启动整台机器。

右边是一条 Cordis 模块轨道。Profile 决定这次启动挂上哪些模块，模块通过稳定 capability seam 提供和消费能力。

上游架构文档明确说，model adapter、tool registry、session log、agent loop 自己也都是插件。所以“Everything is a Plugin”不是“支持第三方扩展”这么简单，而是核心本身也遵循同一组合模型。

但可替换不等于随便替换。契约、依赖、生命周期和行为兼容仍然需要验证。

9:30–12:00｜正式架构：把比喻映射回源码

现在只看六个主元素：
